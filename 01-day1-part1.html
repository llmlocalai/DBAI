03 Databricks Platform Structure

The layered stack, bottom to top

Read the stack from the ground up: storage format, then governance over it, then three ways to move and use the data, then the AI layer that sits on top of all of them and calls back down through governance.

这套技术栈要自下而上地理解：先是存储格式，再是覆盖其上的治理层，然后是三条处理数据的通路，最后是坐在最上层、并通过治理层向下调用的 AI 层。

The single idea underneath all of it: one copy of data, in Delta Lake, governed once by Unity Catalog, then reused by every layer above — warehouse queries, operational apps, and AI agents all read the same governed data instead of each keeping their own silo. That is the literal meaning of "Lakehouse": lake-scale storage with warehouse-grade guarantees, fused.

贯穿整个技术栈的核心思想只有一个：数据只存一份，存在 Delta Lake 里，由 Unity Catalog 统一治理一次，然后被上面每一层复用——数据仓库查询、业务应用、AI 智能体读的都是同一份受治理的数据，而不是各自维护一个数据孤岛。这正是"Lakehouse（湖仓一体）"这个词的字面含义：把数据湖的规模和数据仓库级别的保证融合在一起。

3.2 Unity Catalog: the one layer everything else answers to

Unity Catalog is not one more layer in the stack. It is the governance plane every other layer must check against before it does anything. One namespace, three levels deep: catalog.schema.object. "Object" covers tables, views, volumes (the PDFs in File 2), ML models, UC functions, and now agents and MCP tools — everything gets the same permission model, the same lineage tracking, the same discovery surface.

Unity Catalog 不是技术栈里"又一层"，而是其他每一层在做任何事之前都必须先核对的治理平面。一个命名空间，三级结构：catalog.schema.object。"object"涵盖表、视图、volume（File 2 里的那些 PDF）、机器学习模型、UC 函数，现在也包括智能体和 MCP 工具——所有这些都用同一套权限模型、同一套血缘追踪、同一个发现入口。

Three jobs, concretely: permissions (GRANT/REVOKE at catalog, schema, or object level — this is what let you see or not see the Lakebase index table in File 2's admin step), lineage (which table fed which Delta Live Table fed which agent's answer — traceable end to end), and discovery (search and browse what exists, instead of asking around). Unity Gateway, from 3.1, is this same governance idea extended specifically to LLM calls and agent traffic.

具体做三件事：权限管理（在 catalog、schema 或 object 层级 GRANT/REVOKE——这正是 File 2 管理员步骤里，你能不能看到 Lakebase 索引表的决定因素）、血缘追踪（哪张表喂给了哪条 Delta Live Table，又喂给了哪个智能体的回答——端到端可追溯）、以及发现（搜索和浏览已有资产，而不是靠口口相传）。3.1 里提到的 Unity Gateway，就是这同一套治理思想，专门延伸到了 LLM 调用和智能体流量上。

3.3 Lakehouse family: where data actually lives and moves

Three names, one lineage. Delta Lake is the open table format — the file-level guarantee (ACID transactions, versioning, time travel) that everything else builds on. Lakehouse is the architecture that results from putting warehouse-style analytics directly on top of Delta Lake tables, instead of copying data out to a separate warehouse product. Lakeflow is the family of tools that get data into and through that Lakehouse: ingestion and streaming (100+ connectors), Lakeflow Designer (the nav item you saw as "Visual Data Prep" — a no-code drag-and-drop transform canvas, itself AI-authored by Genie Code), and Lakeflow Jobs (orchestration — the "Runs" nav item is this layer's execution history).

三个名字，一条血脉。Delta Lake 是开放表格式——文件级别的保证（ACID 事务、版本管理、时间回溯），其他一切都建立在它之上。Lakehouse 是把仓库式分析直接架在 Delta Lake 表之上、而不是把数据另外复制到一个单独仓库产品里所形成的架构。Lakeflow 是让数据进入并流经这个 Lakehouse 的一整套工具：数据接入和流处理（100 多个连接器）、Lakeflow Designer（导航里显示为"Visual Data Prep"——一个无代码拖拽式转换画布，由 Genie Code 提供 AI 辅助编写），以及 Lakeflow Jobs（编排调度——导航里的"Runs"就是这一层的执行历史）。

3.4 Lakebase and SQL: the operational and query-facing layer

Lakebase is the odd one out in the family on purpose: a managed serverless Postgres for operational workloads, not analytics. It syncs with the Lakehouse so the same governed data is reachable from both sides. Two jobs specifically: agent state/memory, and the hybrid search index tables from File 1/File 2 (the pgvector + tsvector columns). SQL Warehouses is the compute that actually runs SQL — including the queries a Genie Agent issues behind the scenes. Query History and Alerts, also in the SQL nav section, are monitoring tools on top of that same compute: a log of what ran, and threshold notifications on what a query returns.

Lakebase 故意是这个家族里的"异类"：一个面向业务型工作负载、而不是分析型工作负载的托管无服务器 Postgres。它和 Lakehouse 保持同步，使同一份受治理的数据两边都能访问。具体做两件事：智能体的状态/记忆，以及 File 1/File 2 里讲的混合检索索引表（pgvector + tsvector 那两列）。SQL Warehouses 是真正运行 SQL 的计算资源——包括 Genie Agent 在后台发出的查询。Query History 和 Alerts（同样在 SQL 导航分区里），是架在这同一份计算资源之上的监控工具：一个是"跑过什么"的日志，一个是对查询结果设阈值告警。

Confirmed from the real workspace nav: Lakebase itself is a tab on the Compute page, next to Serverless, SQL warehouses, AI Search, and Apps — not somewhere under Catalog. That placement is consistent, not incidental: Lakebase is something you provision and start, the same category as a SQL warehouse or an AI Search endpoint, not a namespace you merely browse.

已从实际工作区导航确认：Lakebase 本身是 Compute 页面上的一个标签页，和 Serverless、SQL warehouses、AI Search、Apps 排在一起——不在 Catalog 底下。这个位置是一致的，不是偶然的：Lakebase 是你要预置、启动的东西，和 SQL warehouse 或 AI Search 端点属于同一类，不是一个你只是浏览的命名空间。

3.5 Declarative Automation Bundles (DAB): deploying everything above as code

DAB is the layer that turns everything in 3.1-3.4 from a notebook you clicked through into a version-controlled, repeatably deployed project. Formerly named Databricks Asset Bundles (same abbreviation, renamed), it is not the same thing as Databricks Apps (the separate app-hosting console in the product switcher) — a mix-up worth flagging because the names collide easily.

DAB 这一层，把 3.1-3.4 里的所有东西，从一个靠点击操作的 notebook，变成一个纳入版本控制、可重复部署的项目。它原名 Databricks Asset Bundles（缩写不变，改了名字），和产品切换器里那个单独的应用托管控制台 Databricks Apps 不是同一个东西——这两个名字容易混，值得专门提醒一下。

Mechanically: one declarative YAML file, databricks.yml, defines the whole project — resources it can describe include Lakeflow Jobs, Lakeflow pipelines, dashboards, Model Serving endpoints, MLflow Experiments, and registered Models (everything from 3.1 and 3.3 at once). The CLI lifecycle is init (scaffold from a template) → edit databricks.yml → validate → deploy to a target workspace → run. This is what makes a bundle deployable identically to dev, staging, and prod, and what plugs into a GitHub CI/CD workflow instead of a person clicking through a UI each time.

具体机制：一个声明式的 YAML 文件 databricks.yml 定义整个项目——它能描述的资源包括 Lakeflow Jobs、Lakeflow pipeline、仪表盘、Model Serving 端点、MLflow 实验、以及已注册的模型（等于一次性覆盖了 3.1 和 3.3 的内容）。命令行的生命周期是 init（从模板搭建脚手架）→ 编辑 databricks.yml → validate → 部署到目标工作区 deploy → run。这正是让同一个 bundle 能原样部署到开发、预发布、生产环境的原因，也是能接入 GitHub CI/CD 流程、而不必每次都靠人工点界面的原因。

Where you've already seen this pattern

Folder 4's appendix (Agent Bricks CLI) is this same idea applied specifically to agents: an agent.toml file instead of databricks.yml, but the same three-command shape (define, deploy, run). DAB is the general-purpose version of that pattern.

Folder 4 附录里的 Agent Bricks CLI，就是把同一个思路专门用在智能体上：用 agent.toml 代替 databricks.yml，但同样是"定义、部署、运行"三段式。DAB 是这个模式的通用版本。

Advana / FM link

先讲大图景：这节课只回答一个问题——有了文档和一个问题之后，到底是什么机制找到正确的那段内容并交给模型？文件里的所有内容（RAG 流程、提示词/上下文/执行框架的嵌套关系、Genie 与 Knowledge Assistant 与自定义智能体的对比、Lakebase 的两种搜索扩展、混合检索融合）都是对这同一个问题在不同机制层级上的持续回答。

A. Why retrieval agents, and the common pipeline

A model's own knowledge is frozen at training time and has no access to private documents. A retrieval agent closes that gap by running a 4-stage pipeline every time: Indexing (chunk and embed documents once, ahead of time), Retrieval (find the chunks relevant to this question), Generation (the model answers using only those chunks), Feedback (log what was retrieved and how it was used, to improve the next round).

模型自身的知识在训练时就被冻结了，也接触不到私有文档。检索增强智能体通过每次运行一个四阶段流程来弥补这个缺口：索引（提前把文档切块并生成向量，一次性完成）、检索（找到与这个问题相关的那些块）、生成（模型只用这些块来回答）、反馈（记录检索到了什么、怎么被用的，用来改进下一轮）。

B. Prompt Engineering → Context Engineering → Harness Engineering

Three nested levels, each containing the one before it. Prompt engineering: how you phrase the instruction to the model. Context engineering: what information surrounds that instruction — retrieved chunks, conversation history, tool outputs. Harness engineering: the runtime loop, guardrails, observability, and feedback loops that make the whole agent reliable in production, not just smart in a demo. A great prompt inside a weak harness still fails in production.

三个层层嵌套的层级，每一层都包含前一层。提示词工程：怎样表述给模型的指令。上下文工程：这条指令周围有哪些信息——检索到的文本块、对话历史、工具输出。执行框架工程：让整个智能体在生产环境中可靠运行的运行时循环、护栏、可观测性和反馈回路，而不只是在演示里看起来聪明。一个好的提示词放进一个薄弱的执行框架里，到了生产环境照样会失败。

D–E. Lakebase, and hybrid search via RRF

Lakebase is a managed serverless Postgres, positioned for operational workloads — agent state and memory — not analytics, and it syncs with the Lakehouse so the same governed data is reachable from both. Two Postgres extensions do the retrieval work: lakebase_vector (approximate nearest-neighbor semantic search, pgvector-syntax, IVF+RaBitQ quantization) and lakebase_text (BM25 full-text keyword search, tsvector-compatible, Block-Max WAND top-K pushdown). Hybrid search runs both and fuses the two ranked lists with Reciprocal Rank Fusion (RRF): each document's score is the sum of 1/(k+rank) across both lists, so a document that ranks well on meaning but shares zero exact words with the query can still surface — the case a pure keyword search would miss, and a case the lecture's diagram illustrates directly (confirmed readable from the raw file, full SVG and its accessibility label intact).

Lakebase 是托管的无服务器 Postgres，定位是业务型工作负载——智能体的状态和记忆——而不是分析型工作负载，并且会与 Lakehouse 同步，使同一份受治理的数据可以从两边同时访问。两个 Postgres 扩展承担检索工作：lakebase_vector（近似最近邻语义搜索，pgvector 语法，IVF+RaBitQ 量化）和 lakebase_text（BM25 全文关键词搜索，兼容 tsvector，Block-Max WAND 的 top-K 下推）。混合检索同时跑这两种搜索，再用倒数排名融合（RRF）把两个排名列表融合：每个文档的得分是两个列表中 1/(k+rank) 的加总，所以一个在语义上很贴切、但和查询词一个字都不重合的文档，照样能被排到前面——这正是纯关键词搜索会漏掉的情况，讲义里的示意图直接演示了这一点（已确认可从原始文件中完整读取，包括 SVG 图形和它的无障碍文字说明）。

"IVF+RaBitQ quantization" is a name-drop here — File 8's appendix opens up exactly what IVF means mechanically (how the partitioning actually works) and adds the GUCs you'd tune it with.

这里的"IVF+RaBitQ 量化"只是先点个名——File 8 附录会把 IVF 到底怎么运作讲透，还会给出调它用的那几个 GUC 参数。

The RRF query proves this structurally: it runs two independent RANK() OVER (...) subqueries (LIMIT 40 each) before fusing them with COALESCE(1.0/(60+v.rank),0) + COALESCE(1.0/(60+k.rank),0) AS rrf_score — ranking is a post-retrieval step applied to whatever indexing already made fast to retrieve.

切分和建索引是构建时、只做一次的；排序发生在查询时；向量化横跨两边——建索引时对每个文本块做一次，查询时对问题再做一次。RRF 查询在结构上证明了这一点：先跑两个独立的 RANK() OVER (...) 子查询（各 LIMIT 40），再用 COALESCE(1.0/(60+v.rank),0) + COALESCE(1.0/(60+k.rank),0) AS rrf_score 融合——排序是索引已经让检索变快之后，加在检索结果之上的后处理步骤。

-- B3: vector similarity (cosine distance, lower = more similar)
SELECT chunk_text, embedding <=> '<1024-dim vector>' AS distance
FROM doc_chunks ORDER BY distance;                        -- ~0.501

-- B4: keyword search (BM25, negative score, ascending = best first)
SELECT *, chunk_tsvector <@> to_bm25query(
  to_tsvector('english','Victorian'), 'doc_chunks_ts_idx') AS score
FROM doc_chunks ORDER BY score;                            -- ~-0.556

-- B5: hybrid, RRF over independently ranked top-40 lists
WITH vector_ranked AS (
  SELECT chunk_id, RANK() OVER (ORDER BY dist) AS rank FROM (
    SELECT chunk_id, embedding <=> '<vec>' AS dist
    FROM doc_chunks ORDER BY dist LIMIT 40) v),
keyword_ranked AS (
  SELECT chunk_id, RANK() OVER (ORDER BY score) AS rank FROM (
    SELECT chunk_id, chunk_tsvector <@> to_bm25query(
      to_tsvector('english','Victorian'),'doc_chunks_ts_idx') AS score
    FROM doc_chunks ORDER BY score LIMIT 40) k)
SELECT d.chunk_id, LEFT(d.chunk_text,120) AS preview,
  COALESCE(1.0/(60+v.rank),0) + COALESCE(1.0/(60+k.rank),0) AS rrf_score
FROM doc_chunks d
LEFT JOIN vector_ranked v ON d.chunk_id = v.chunk_id
LEFT JOIN keyword_ranked k ON d.chunk_id = k.chunk_id
WHERE v.chunk_id IS NOT NULL OR k.chunk_id IS NOT NULL
ORDER BY rrf_score DESC LIMIT 10;

Two operators did real work above without being named: <=> is vector_cosine_ops, and <@> is the BM25 distance operator. Both, plus the lakebase_ann index these queries lean on for speed, get their full explanation in File 8's appendix — including the two other distance operators (<->, <#>) this lab didn't need but you may.

上面用到了两个没点名解释的操作符：<=> 是 vector_cosine_ops，<@> 是 BM25 距离操作符。这两个，加上这些查询靠它提速的 lakebase_ann 索引，完整讲解都在 File 8 附录 里——还包括这个 lab 没用到、但你可能会用到的另外两种距离操作符（<->、<#>）。

The deepest idea isn't any one function — it's that ai_prep_search produces two different columns from the same chunk, one to embed and one to retrieve.

先讲大图景：这是前面每一节都说"还没讲到"所指的那个文件。四个 SQL AI 函数，各负责把 PDF 变成可检索数据这条流水线上的一环：ai_parse_document（解析——已确认就是 Content Search 背后用的那个函数）、ai_classify 和 ai_extract（元数据）、ai_prep_search（切分）。最深的那个想法不是任何一个函数本身——而是 ai_prep_search 从同一个文本块产出两个不同的列，一个用来向量化，一个用来检索。

A-C. Parse, classify, extract

ai_parse_document(content, MAP('version','2.0')) against a volume returns a VARIANT (structured JSON) with layout-aware text — document:elements and document:pages. variant_explode turns that JSON into queryable rows. ai_classify assigns a label from a defined set (routing logic — which processing path a document takes); ai_extract pulls named fields into real columns. 对一个 volume 调用 ai_parse_document(content, MAP('version','2.0'))，返回一个带版式信息的结构化 JSON（VARIANT），拆成 document:elements 和 document:pages。variant_explode 把这个 JSON 变成可查询的行。ai_classify 从一组预定义标签里选一个（路由逻辑——文档走哪条处理路径）；ai_extract 把命名字段抽取成真正的列。两者都会拼接到文本块表里作为元数据，这正是后面 AI Search 能按文档类型或抽取字段过滤、排序，而不只靠语义相似度的原因。

D. Chunking principles, and the embed/retrieve split

ai_prep_search chunks using AI-found semantic boundaries instead of fixed character counts. Three stated principles: chunk size must respect the embedding model's context window (overflow is silently truncated — a dangerous failure mode, nothing errors); 10-20% overlap prevents information loss at boundaries; smaller chunks are more precise but lose context, larger chunks keep context but dilute signal. The "Lost in the Middle" phenomenon (LLMs attend less to information buried mid-context than at the start or end) is given as the reason to favor smaller, focused chunks.

ai_prep_search 用 AI 找到的语义边界切分，而不是固定字符数。文中给出三条原则：chunk 大小必须符合向量模型的上下文窗口（超出部分会被静默截断——危险的失败模式，不会报错）；10-20% 的重叠能防止边界处信息丢失；块越小越精确但失去上下文，块越大保留上下文但信号被稀释。"Lost in the Middle"（迷失在中间，大语言模型对长上下文中间部分的关注度低于开头和结尾）被直接点名，作为偏好更小、更聚焦的块的理由。

chunk_to_embed ≠ chunk_to_retrieve

Embedding answers "what is this chunk about?" — gets surrounding context prepended (headers, section titles) so the vector lands in the right region of vector space. The lecture's example: "The fee is $50" alone embeds meaninglessly; "Cleaning Policy > Late Checkout: The fee is $50" is findable. Retrieval answers "what should the LLM read?" — the clean original text, no prepended metadata, since that would waste context and risk confusing generation. Rule: optimize for findability when embedding, optimize for readability when retrieving.

向量化回答"这个块讲的是什么"——会加上周边上下文（标题、章节名），让向量落在向量空间里正确的区域。课程例子：单独的 "The fee is $50" 向量化毫无意义；"Cleaning Policy > Late Checkout: The fee is $50" 就能被找到。检索回答"应该给模型读什么"——是没有附加元数据的干净原文，因为那会浪费上下文、还可能干扰生成。原则：向量化时为"可被找到"优化，检索时为"可读性"优化。

The hard question: can this ever be 100% accurate?

No, and that's the insight worth sitting with. "100% accurate" conflates two different properties: repeatable (same input, same output, every run) and correct (matches the real number on the page). OCR on a scanned document is already lossy and probabilistic before any AI model runs; the LLM behind ai_extract adds a second probabilistic layer on top. Neither hits 100% correct on every input, regardless of prompt or model. The fix is not to chase determinism in the extraction step — it's to move determinism into the acceptance step. The AI's job becomes "produce a candidate," not "be right"; a fully deterministic gate (independent source cross-check, arithmetic closure, format/schema validation, table-vs-narrative agreement — steps 4-5 above, restated as a ranked list) decides whether that candidate is trusted. Confidence scores and prompt tuning never decide acceptance; SQL and reference data do, which is what makes the gate auditable. Human review doesn't disappear — it moves from "read the whole packet" to "read only what failed a gate."

不能，而这正是值得停下来想清楚的地方。"100% 准确"混淆了两件不同的事：可重复（同样输入，每次都跑出同样结果）和正确（和纸面上的真实数字一致）。扫描文档的 OCR 本身在任何 AI 模型介入之前就已经是有损、概率性的；ai_extract 背后的大语言模型又在上面叠加了一层概率性判断。无论怎么调提示词、换模型，都做不到每次输入都 100% 正确。解法不是在抽取这一步追求确定性，而是把确定性搬到验收这一步。AI 的任务变成"产出一个候选值"，不是"必须做对"；一组完全确定性的关卡（独立数据源交叉核对、算术闭合、格式/schema 校验、表格与叙述文本一致性——就是上面第 4、5 步换个角度重新排序）决定这个候选值是否被信任。置信度分数和提示词调优从不参与这个决定，SQL 和参照数据才参与，这正是这道关卡可审计的原因。人工审核并未消失，只是从"读整份文件"变成"只读没通过关卡的那部分"。

A. Distance metrics: three operator classes, one choice to make per index

When you build a lakebase_ann index, you pick an operator class — this is the one decision that has to match how your embedding model was actually trained, not a style preference. Cosine (<=>, vector_cosine_ops) measures the angle between two vectors, ignoring their length — the default for almost all text embedding models, including every databricks-*-embedding model used across this notebook. L2/Euclidean (<->, vector_l2_ops) measures straight-line distance and cares about magnitude — use it only when absolute spatial distance is meaningful and your vectors are deliberately not normalized. Inner product (<#>, vector_ip_ops) is a faster shortcut that gives the identical ranking as cosine, but only when every vector is already normalized to unit length — otherwise it silently gives wrong rankings, which is why it is correctly the least-used of the three.

建 lakebase_ann 索引时要选一个操作类（operator class）——这是唯一一个必须和你的向量模型实际训练方式匹配的决定，不是风格偏好。Cosine（余弦）（<=>，vector_cosine_ops）衡量两个向量之间的夹角，不管长度——几乎所有文本向量模型的默认选择，包括本笔记里用到的每一个 databricks-*-embedding 模型。L2/欧几里得（<->，vector_l2_ops）衡量直线距离，关心长度——只有当绝对空间距离本身有意义、且向量故意不做归一化时才用它。内积（Inner product）（<#>，vector_ip_ops）是一条更快的捷径，排序结果和 cosine 完全一致——但前提是每个向量都已经归一化为单位长度，否则会悄悄给出错误的排序，这正是三者中它最少被用到的原因。

B. IVF: how lakebase_ann actually partitions the vector space

Exact nearest-neighbor search compares a query against every row — correct, but too slow once a table has more than a few thousand vectors. lakebase_ann uses IVF (Inverted File): at build time, it clusters all vectors into partitions ("lists") around a set of centroids. At query time, the query vector is compared only against the centroids, and only the nearest few partitions actually get scanned — everything else is skipped entirely, never touched. This is the literal mechanism behind the "approximate" in "approximate nearest-neighbor": a vector sitting just outside a scanned partition's boundary can be missed even if it would have ranked well, which is the recall you're trading away for speed.

精确最近邻搜索要拿查询向量和每一行逐个比较——结果准确，但表一旦超过几千条向量就会慢得不实用。lakebase_ann 用的是 IVF（倒排文件）：建索引时，先把所有向量围绕一组中心点（centroid）聚类成若干个分区（"list"）。查询时，查询向量只和这些中心点比较，只有最近的几个分区真正被扫描——其余分区被完全跳过，连碰都不碰。这正是"近似最近邻"里"近似"二字的字面机制：一个刚好落在被扫描分区边界之外的向量，即便本来排名靠前，也可能被漏掉——这就是用速度换来的那部分召回率损失。

D. BM25: three factors, and why it beats Postgres' built-in ts_rank

lakebase_bm25 ranks keyword matches using three factors combined: term frequency (how often the term appears in this document — more occurrences, more relevant), inverse document frequency (a term that is rare across the whole corpus counts for more than one that appears everywhere — "reprogramming" matters more than "the"), and length normalization (a long document doesn't win purely by being long enough to mention the term more times by chance). Postgres' built-in ts_rank has no equivalent to the second factor — it scores each document in isolation, with no sense of what's rare or common across the whole collection — which is why BM25 scores stay stable and meaningful as the corpus grows and ts_rank's don't.

lakebase_bm25 综合三个因素给关键词匹配打分：词频（这个词在这篇文档里出现了多少次——出现越多，相关性越高）、逆文档频率（在整个语料库里越少见的词，权重越高——"reprogramming"比"the"更有信息量）、以及长度归一化（一篇长文档不能单靠篇幅长、碰巧多提了几次这个词就赢）。Postgres 自带的 ts_rank 没有第二个因素的对应物——它只孤立地给每篇文档打分，不知道整个语料库里哪些词常见、哪些稀有——这正是为什么语料库越大，BM25 的分数越稳定、越有意义，而 ts_rank 做不到这一点。

The algorithm-level answer to Section 4.1's "why so many names" — IVF vs. HNSW

This file is also where Section 4.1's two-backend split gets its deepest technical grounding. Lakebase Search's ANN is IVF — cluster into partitions, scan a few, tune with probes/epsilon/prefilter. AI Search's ANN (File 6) is HNSW — a navigable graph structure, walked greedily from an entry point toward the query, no partitions and no exposed GUCs in this course's material because it's a fully managed service. Different algorithm, same contract: approximate, not exact, nearest-neighbor search, trading a small amount of recall for large speed gains at scale. The practical consequence: Lakebase Search gives you dials because you own the Postgres instance; AI Search gives you a service-level guarantee instead, because Databricks owns the tuning.

这份文件也是 Section 4.1 "为什么有这么多名字"那个两后端划分，在算法层面最深的落脚点。Lakebase Search 的 ANN 是 IVF——聚类分区、扫描少数几个、靠 probes/epsilon/prefilter 调优。AI Search（File 6）的 ANN 是 HNSW——一种可导航的图结构，从一个入口点贪心地往查询方向走，没有分区，这门课的材料里也没给出任何可调的 GUC，因为它是完全托管的服务。算法不同，契约相同：都是近似、而非精确的最近邻搜索，用一点召回率换来规模化场景下的大幅提速。实际的结果是：Lakebase Search 给你旋钮，因为你自己掌握着那个 Postgres 实例；AI Search 给你的是服务级别的保证，而不是旋钮，因为调优的事由 Databricks 负责。

6.2 Meta-harness: the layer above File 2's "Agent" from Section 3.1

New vocabulary, precisely defined, that refines Section 3.1's AI-layer table. An agent is a process for one task with a set of tools. A harness is the runtime that wires those pieces together (which models get called, how tools are invoked, how state and traces are captured) — Claude Code and Cursor are named explicitly as examples. A meta-harness sits above individual harnesses: one place to register different harnesses, compose agents that use more than one, and apply consistent policy and observability across all of them, without standardizing on a single framework. Omnigent is Databricks' open-source meta-harness implementing this.

新词汇，但定义精确，正好细化了 3.1 节 AI 层那张表。智能体（agent）是针对一项任务、配一套工具的进程。执行框架（harness）是把这些部件接在一起的运行时（调用哪些模型、怎么调用工具、怎么捕获状态和追踪记录）——文中明确举了 Claude Code 和 Cursor 作为例子。元执行框架（meta-harness）坐在各个具体执行框架之上：一个统一的地方来注册不同的执行框架、组合用到多个执行框架的智能体、并对所有这些统一施加策略和可观测性，而不需要统一到单一框架上。Omnigent 就是 Databricks 实现这一思路的开源元执行框架。

Where this sits relative to what you already learned

Section 3.1's "Agents" (AI/ML nav) is a harness-level tool — it builds one custom agent. A meta-harness is one level above that: the thing that lets you run a Genie Agent, a custom Agent, and a third-party framework's agent side by side under one set of policies. This is the missing piece between "I built an agent" and "my organization runs agents as a system," which is the ebook's central distinction.

3.1 节里 AI/ML 导航下的"Agents"，是执行框架层面的工具——它负责搭建一个自定义智能体。元执行框架比它高一层：让你能把一个 Genie Agent、一个自定义 Agent、以及第三方框架搭的智能体，放在同一套策略下并排运行的那个东西。这正是"我搭了一个智能体"和"我的组织把智能体当作一套系统来运行"之间缺的那一块，也是这份电子书的核心区分。
