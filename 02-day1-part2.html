A What are AI Agents?

A1 Single Agents

An AI agent is a model wrapped in a loop that can take actions and react to their results, instead of mapping one prompt straight to one response. The loop has four moves: reason and plan (break a goal into steps instead of answering in one shot), use tools (call functions, query data, reach external systems for real information), observe and adapt (read each tool result and decide the next action, looping until the goal is met), and stay grounded (rely on retrieved, governed data rather than the model's frozen training knowledge). On Databricks specifically, the tools an agent calls are Unity Catalog functions: governed, discoverable, and permission-checked, which is what makes agent actions auditable in production.

AI agent 就是把模型包进一个能采取行动、并根据行动结果做反应的循环里，而不是一个提示对应一个回答。这个循环有四个动作：推理和规划（把目标拆成步骤，而不是一次答完）；使用工具（调用函数、查询数据、连接外部系统来获取真实信息）；观察和调整（读取每次工具调用的结果，决定下一步，循环直到目标达成）；保持有据可依（依赖检索到的、受治理的数据，而不是模型训练时就冻结的知识）。具体到 Databricks：agent 调用的工具就是 Unity Catalog 函数——受治理、可被发现、经过权限检查，这正是让 agent 的行为在生产环境里可审计的原因。

A2 Multi-Agent Supervisors

The supervisor-worker pattern (also called router-delegate) is the common way to go from one agent to several. A supervisor agent receives the request, analyzes intent, and delegates to the right specialized worker (a data agent for Unity Catalog functions and SQL, a research agent for AI Search over documents, a general agent for reasoning that needs no tools), then synthesizes the worker's result back into a response. In the OpenAI Agents SDK this delegation is a first-class concept called a handoff: Agent(name="Supervisor", instructions="Route requests to the appropriate specialist.", handoffs=[data_agent, business_agent]).

supervisor-worker 模式（也叫 router-delegate，路由-分派）是从单 agent 扩展到多 agent 最常见的做法。一个 supervisor agent 接收请求、分析意图，把任务分派给合适的专职 worker（负责 Unity Catalog 函数和 SQL 的 data agent、负责在文档上做 AI Search 的 research agent、不需要工具、只做推理的 general agent），再把 worker 的结果整合成最终回答。在 OpenAI Agents SDK 里，这种分派是一个一等概念，叫 handoff：Agent(name="Supervisor", instructions="Route requests to the appropriate specialist.", handoffs=[data_agent, business_agent])。

A4 Agents on Databricks: the spectrum

Databricks offers three starting points for building an agent, trading customization for managed convenience. Knowledge Assistant (legacy) lets you bring your own AI Search index and chunking strategy with full retrieval control, but is a legacy path. Genie Agent (managed, recommended for data-aware agents) is declarative: you attach tables or UC volumes and Databricks handles tool orchestration and query generation. Custom Agent (code-first) is where you own the agent logic, tools, and orchestration end to end, deployed as a Databricks App, the platform's recommended hosting path.

在 Databricks 上搭 agent 有三个起点，分别在"可定制"和"托管便利"之间做不同取舍。Knowledge Assistant（旧版）让你自带 AI Search 索引和分块策略，对检索管线有完全控制权，但属于一条 legacy 路径。Genie Agent（托管，官方推荐用于数据感知型 agent）是声明式的：你只需要挂上表或 UC volume，Databricks 负责工具编排和查询生成。Custom Agent（代码优先）是你从头到尾自己掌控 agent 逻辑、工具和编排，部署成 Databricks App，这是平台推荐的托管方式。

B Tools and Common Patterns

B1 Model Context Protocol (MCP)

MCP is an open standard for connecting agents to tools and context. Databricks managed MCP servers are Databricks-hosted, ready-to-use endpoints for AI Search, Genie Agents, Databricks SQL, and Unity Catalog functions. The payoff is standardization: define a tool once, and any MCP-aware client or framework can discover its schema at runtime and call it, instead of every framework needing bespoke glue to reach every tool (an N-frameworks by M-tools integration problem). Unity Catalog permissions stay enforced underneath, and usage is tracked and managed through Unity Gateway.

MCP 是一个开放标准，用来把 agent 连接到工具和上下文。Databricks 托管的 MCP 服务器是 Databricks 自己托管的、开箱即用的端点，覆盖 AI Search、Genie Agent、Databricks SQL 和 Unity Catalog 函数。它带来的好处是标准化：工具只定义一次，任何支持 MCP 的客户端或框架都能在运行时发现它的 schema 并调用它，而不需要每个框架都为每个工具写一套定制胶水代码（否则就是一个 N 个框架 × M 个工具的集成难题）。底层的 Unity Catalog 权限始终生效，使用情况通过 Unity Gateway 跟踪和管理。

B2 Genie Agents: single agent with on-behalf-of governance

A Genie Agent is a managed single agent whose main tool is text-to-SQL (optionally augmented with trusted UC functions you attach). The part that matters for an enterprise deployment is the governance model around it, not just the SQL generation. The user authenticates as themselves; the agent's access-control list decides whether they can view or run it; and every query then executes on behalf of that user: the SQL warehouse borrows the agent author's compute delegation (configured once, at setup time), but data access is enforced against the requesting user's own Unity Catalog permissions, including row filters and column masks, and every query is audited back to that user, not to a shared service account.

Genie Agent 是一个托管的单 agent，它的主要工具是 text-to-SQL（可以再加上你附加的受信任 UC 函数）。对企业级部署来说，真正重要的是它周围的治理模型，而不只是 SQL 生成本身。用户以自己的身份登录；agent 的访问控制列表决定他能不能查看或运行它；然后每一次查询都是"代表该用户"执行：SQL 仓库借用的是 agent 作者在配置时设定好的算力委托，但数据访问是按照发起请求的那个用户自己的 Unity Catalog 权限（包括行过滤和列遮蔽）来强制执行的，每一次查询都会被审计到那个具体用户身上，而不是归到一个共享的服务账号下。

Advana / FM link

This is the governance pattern that answers a question FM Insight will face immediately: if a Genie Agent sits over GFEBS or Navy ERP tables, two different auditors with different row-level access to the same ledger must get different answers from the same agent, automatically, without anyone writing per-user logic into the agent itself. On-behalf-of execution is exactly that mechanism, built into the platform rather than something FM Insight would have to engineer by hand. 这个治理模型正好回答了 FM Insight 马上就会遇到的一个问题：如果一个 Genie Agent 架在 GFEBS 或 Navy ERP 的表上面，两位对同一本总账有不同行级访问权限的审计员，必须从同一个 agent 那里自动得到不同的答案，而不需要任何人在 agent 里手写按用户区分的逻辑。On-behalf-of 执行机制正是做这件事的平台内置能力，而不是 FM Insight 需要自己手工搭建的东西。这也给 Folder 3/4 留了一个值得深挖的问题：返回给受限用户的审计证据引用，会不会通过被引用文档本身的文本内容泄露出行过滤拦不住的范围信息。

C Governance and AI Management with Unity Gateway

Unity Gateway is the platform's central governance layer for LLM endpoints, MCP servers, and coding agents. It gives six things at once: governance (tracking which users, agents, and applications make which calls, with on-behalf-of execution for MCP so agents act with the requesting user's own permissions instead of a shared service account), rate limiting (per-endpoint and per-identity QPM/TPM caps), guardrails (input/output safety and data-protection filters), usage tracking (token consumption and cost across endpoints), payload logging (request/response audit trails via inference tables), and hard spend caps. Without it, every agent or application would have to build its own access control, guardrails, and logging from scratch, which gets unreliable fast once more than one model or provider is in play.

Unity Gateway 是平台针对 LLM 端点、MCP 服务器和编码 agent 的中央治理层。它一次性提供六样东西：治理（跟踪哪些用户、agent、应用在发起哪些调用，MCP 场景下用 on-behalf-of 执行方式，让 agent 用发起请求的那个用户自己的权限行事，而不是用一个共享服务账号）、速率限制（按端点和按身份设 QPM/TPM 上限）、护栏（输入输出的安全过滤和数据保护策略）、用量跟踪（跨端点的 token 消耗和成本）、payload 日志（通过推理表记录请求/响应审计轨迹）、硬性花费上限。没有它，每个 agent 或应用都得从零开始自己搭访问控制、护栏和日志，一旦涉及一个以上的模型或供应商，这套自建的东西很快就会变得靠不住。

C1 Fallback Routing

Unity Gateway endpoints support fallback routing: a request goes to a primary model, and on a 429 or 5xx error, the gateway retries against a configured fallback model, then a second fallback if needed, logging every attempt (success or failure) to an inference and usage-tracking table. The point is availability without the caller having to implement retry logic itself.

Unity Gateway 端点支持 fallback 路由：请求先发到主模型，一旦遇到 429 或 5xx 错误，gateway 会自动重试到配置好的备用模型，需要的话再试第二个备用模型，并把每一次尝试（无论成功失败）都记到推理和用量跟踪表里。这样做的意义是：调用方不需要自己写重试逻辑，也能获得可用性保障。

C2 Workspace-Scoped Endpoints vs. Model Services

Legacy model serving endpoints are workspace-scoped: the same endpoint gets duplicated per workspace, with permissions managed separately in each. Databricks recommends moving most governed LLM use cases to model services instead: a Unity Catalog securable object, defined once in a catalog.schema, shared across the metastore, discoverable in Catalog Explorer, and governed centrally through Unity Gateway controls rather than per-workspace permissions.

旧版的 model serving 端点是"按 workspace 划定作用域"的：同一个端点要在每个 workspace 里各建一份，权限也要在每个 workspace 里分别管理。Databricks 建议大多数受治理的 LLM 使用场景改用 model services：它是一个 Unity Catalog 可授权对象，在某个 catalog.schema 下定义一次，就能在整个 metastore 范围内共享，可以在 Catalog Explorer 里被发现，并且通过 Unity Gateway 的控制手段统一治理，而不是按 workspace 各自维护权限。

A technical wrinkle worth keeping: sync vs. async on Serverless

Notebook cells on Serverless already run inside a live asyncio event loop. Serverless 上的 notebook 单元本身就跑在一个活着的 asyncio 事件循环里。同步版本的 call_tool() 是一个便利封装，内部试图桥接进那个已经在跑的事件循环，而这样把一个事件循环嵌套进另一个事件循环，可能会抛出一个逃过普通 try/except 的 ExceptionGroup。解决办法是从头到尾保持异步：用 await acall_tool() 和 await asyncio.sleep()，Databricks Serverless 支持在单元里直接写顶层 await。

B The Broken Documentation

The function as registered:

def est_listing_value(
    p1: float,
    p2: float,
    p3: str
) -> str:
    """
    Calculates value.

    Args:
        p1: price
        p2: count
        p3: market

    Returns:
        str: result
    """
    base_value = p2 * 365 * 0.7  # assume 70% occupancy
    bedroom_factor = 1 + (p1 - 1) * 0.15
    if p3.lower() == 'entire home/apt':
        multiplier = 1.2
    elif p3.lower() == 'private room':
        multiplier = 0.8
    else:
        multiplier = 0.5
    estimated = base_value * bedroom_factor * multiplier
    return f"Estimated annual revenue: ${estimated:,.2f}"

Read the code, not the docstring, and the mismatch is immediate: the docstring says p1 is the price and p2 is a count, but the code multiplies p2 as if it were the nightly price and uses p1 as the bedroom count — the two are swapped relative to what the docstring claims. p3 fares no better: anything that isn't exactly "entire home/apt" or "private room" — including a city name like "San Francisco" — silently falls through to the lowest multiplier instead of raising an error. The function never fails. It just produces a confident, wrong, dollar-shaped number.

去读代码而不是 docstring，问题立刻就看出来了：docstring 说 p1 是价格、p2 是数量，但代码里是把 p2 当夜间价格来乘，p1 当卧室数来用——两者和 docstring 说的正好对调。p3 也一样糟：只要不是精确等于 "entire home/apt" 或 "private room" 的任何值——包括像 "San Francisco" 这样的城市名——都会默默落到最低档乘数，而不是报错。这个函数从来不会失败，它只会给出一个自信、错误、但看起来像钱的数字。

C Fix the Function

The fix touches only documentation and parameter names — the arithmetic inside the function body does not change at all. Three things change: the parameter names become descriptive and typed (nightly_price_usd: float, num_bedrooms: float, room_type: str), the one-line description becomes a real explanation of what is computed and when to use the tool, and the Args/Returns sections become specific enough that a model can get every value right on the first try, including listing the exact three strings room_type accepts.

这次修复只动了文档和参数名，函数体里的计算逻辑一行都没改。改的是三件事：参数名变得有意义且带类型（nightly_price_usd: float、num_bedrooms: float、room_type: str）；原来一句话的描述变成了真正说明这个函数算的是什么、什么时候该用；Args/Returns 部分写得足够具体，模型第一次就能把每个值填对，包括把 room_type 能接受的三个字符串原样列出来。

def est_listing_value(
    nightly_price_usd: float,
    num_bedrooms: float,
    room_type: str
) -> str:
    """
    Estimate the annual revenue for a San Francisco Airbnb listing based on
    its nightly price, number of bedrooms, and room type. Assumes 70%
    occupancy year-round.

    Use this tool when a user asks how much a listing could earn per year.

    Args:
        nightly_price_usd: The nightly price of the listing in US dollars (e.g. 250.0).
        num_bedrooms: The number of bedrooms in the listing (e.g. 1, 2, 3). A
            studio should be passed as 1. Each additional bedroom beyond
            the first increases the estimate by 15%.
        room_type: The Airbnb room type. Must be exactly one of:
            "Entire home/apt", "Private room", or "Shared room".

    Returns:
        A string describing the estimated annual revenue in USD.
    """
    base_value = nightly_price_usd * 365 * 0.7  # assume 70% occupancy
    bedroom_factor = 1 + (num_bedrooms - 1) * 0.15
    if room_type.lower() == 'entire home/apt':
        multiplier = 1.2
    elif room_type.lower() == 'private room':
        multiplier = 0.8
    else:
        multiplier = 0.5
    estimated = base_value * bedroom_factor * multiplier
    return f"Estimated annual revenue: ${estimated:,.2f}"

A OpenAI Agent Orchestration Patterns

The OpenAI Agents SDK splits orchestration into two families. LLM-driven orchestration means the model itself decides what happens next — which specialist to call, whether to keep going. Code-driven orchestration means your Python code controls the flow deterministically, and the model only fills in each individual step. Neither is strictly better; the choice is about how much control versus flexibility a given workflow needs.

OpenAI Agents SDK 把编排方式分成两大类。LLM 驱动（LLM-driven）编排是模型自己决定接下来发生什么——该调用哪个专家、要不要继续。代码驱动（code-driven）编排是你的 Python 代码确定性地控制整个流程，模型只负责填好每一个具体步骤。两者没有绝对的好坏之分，怎么选取决于这个具体工作流到底需要多少控制力、又能容忍多少灵活性。

A1 · LLM-Driven Orchestration: Handoffs vs. Agents as Tools

An agent in this framework is an LLM equipped with instructions, tools, and handoffs — the ability to delegate a task to a specialized sub-agent. There are two distinct ways to delegate, and they differ in who ends up owning the conversation.

在这套框架里，agent 就是一个配好了指令、工具、以及handoffs（转交）能力的 LLM——handoffs 就是把任务委托给一个专门化的子 agent 的能力。委托有两种截然不同的方式，区别在于最后谁来"拥有"这段对话。

Handoffs (Agent(handoffs=[agent_a, agent_b])): a triage or supervisor agent routes the conversation to a specialist, and the specialist then becomes the active agent and responds directly to the user. Conversation ownership transfers completely; the supervisor does not see or post-process the specialist's reply. Use this when the specialist should respond directly, when prompts need to stay focused per route, or when each route needs its own distinct instructions and tool set.

Handoffs（Agent(handoffs=[agent_a, agent_b])）：一个分诊/主管 agent 把对话路由给某个专家，这个专家接手之后就变成了当前负责对话的 agent，直接回复用户。对话的所有权完全转移过去；主管看不到也不会再加工专家的回复。适合用在：希望专家直接回复用户、每条路由需要保持自己专注的 prompt、或者每条路由需要完全不同的指令和工具集这些场景。

Agents as Tools (Agent(tools=[specialist.as_tool()])): a manager agent keeps conversation control the whole time and invokes specialist agents the same way it would invoke any other tool, via Agent.as_tool(). The manager reads each specialist's output and synthesizes a final answer itself. Use this when one agent should own the final answer, combine outputs from several specialists, or maintain a single uninterrupted conversational thread.

Agents as Tools（把 agent 当工具用）（Agent(tools=[specialist.as_tool()])）：一个经理 agent 全程保持对话控制权，像调用任何其他工具一样，通过 Agent.as_tool() 去调用专家 agent。经理会读取每个专家的输出，自己综合出最终答案。适合用在：希望由一个 agent 来拥有最终答案、需要整合多个专家的输出、或者希望保持一条不被打断的单一对话线这些场景。

A2 · Code-Driven Orchestration

Code-driven orchestration trades some of the model's autonomy for predictability over speed, cost, and the order things happen in. Four patterns recur: structured outputs (an agent returns typed data your code branches on, e.g. routing by classification), sequential chaining (one agent's output feeds the next — research → outline → draft → review), parallel execution (independent agents run concurrently via asyncio.gather), and feedback loops (a generator and an evaluator agent iterate until the evaluator approves or a max-iteration count is hit).

代码驱动编排是用模型的一部分自主性，换取在速度、成本、执行顺序上的可预测性。常见的有四种模式：结构化输出（agent 返回带类型的数据，你的代码据此分支，比如按分类结果路由）；顺序链式（一个 agent 的输出喂给下一个——研究 → 大纲 → 草稿 → 审阅）；并行执行（用 asyncio.gather 并发跑多个相互独立的 agent）；反馈循环（一个生成 agent 和一个评估 agent 反复迭代，直到评估通过或者达到最大迭代次数）。

Two implementation details matter across all of these: Runner.run() always returns a RunResult object, so chaining must extract .final_output (for passing a plain value forward) or .to_input_list() (for carrying the full conversation history, including tool calls, forward to the next agent — to_input_list() is the one to prefer in sequential chaining, since final_output alone drops that history). And a feedback-loop evaluator needs a structured output_type (e.g. a Pydantic model with approved: bool and feedback: str) so its verdict can be parsed programmatically rather than scraped from free text.

这四种模式里有两个实现细节是共通的：Runner.run() 永远返回一个 RunResult 对象，所以链式调用时要么取 .final_output（只往下传一个纯值），要么取 .to_input_list()（把包括工具调用在内的完整对话历史往下传给下一个 agent——顺序链式更推荐用 to_input_list()，因为只用 final_output 会把这段历史丢掉）。另外，反馈循环里的评估 agent 需要一个结构化的 output_type（比如一个带 approved: bool 和 feedback: str 字段的 Pydantic 模型），这样它给出的判断才能被代码直接解析，而不是从一段自由文本里硬抠。

B1 · From Prototype to Governed Tool

A prototyped tool lives only in that one notebook session. The recommended path from there is identical in every framework: register the logic as a Unity Catalog function so it becomes governed and reusable, then let agents reach it through a Managed MCP server — exactly the pipeline File 10 and File 11 already walked through end to end for UC functions specifically. What differs per framework is only how the agent connects to that governed tool afterward: the OpenAI Agents SDK uses McpServer (Section C, below), LangChain discovers tools with DatabricksMCPClient and wraps each as a StructuredTool, and DSPy converts MCP tools with dspy.Tool.from_mcp_tool(...).

一个原型工具只存在于那一次 notebook 会话里。从这里往下，推荐路径在三个框架里是一样的：把逻辑注册成 Unity Catalog 函数，让它变得受治理、可复用，再让 agent 通过托管 MCP 服务器去访问它——这正是 File 10 和 File 11 已经完整走过一遍的 UC 函数流水线。不同框架唯一的差别，是 agent 之后怎么连到这个受治理的工具：OpenAI Agents SDK 用 McpServer（下面 Section C 讲）；LangChain 用 DatabricksMCPClient 发现工具，再把每个工具包成一个 StructuredTool；DSPy 用 dspy.Tool.from_mcp_tool(...) 转换 MCP 工具。

C Databricks MCP Tools with McpServer

Production OpenAI Agents SDK code reaches governed UC tools through databricks_openai.agents.McpServer, which connects agents to Unity Catalog functions, AI Search indexes, and other Databricks services through MCP. It is layered: the agent layer treats each McpServer as a source of tools and calls tools/list to discover and tools/call to invoke; the McpServer class itself extends the SDK's MCPServerStreamableHttp, adding Databricks OAuth authentication, automatic URL construction, and built-in MLflow tracing (every tool call is wrapped with @mlflow.trace(span_type=SpanType.TOOL) automatically); the protocol layer handles the actual Streamable HTTP connection and token refresh with no manual token management needed; and the Unity Catalog backend is what actually executes the call, with UC permissions always enforced against the authenticated caller.

生产环境里的 OpenAI Agents SDK 代码，是通过 databricks_openai.agents.McpServer 去访问受治理 UC 工具的，它通过 MCP 把 agent 连到 Unity Catalog 函数、AI Search 索引，以及其他 Databricks 服务上。这套结构是分层的：agent 层把每个 McpServer 当作工具来源，调 tools/list 发现工具、调 tools/call 调用工具；McpServer 类本身继承自 SDK 的 MCPServerStreamableHttp，在此之上加了 Databricks OAuth 认证、自动构建 URL，以及内置的 MLflow tracing（每次工具调用都会自动被 @mlflow.trace(span_type=SpanType.TOOL) 包一层）；协议层负责真正的 Streamable HTTP 连接和令牌刷新，完全不需要手动管理令牌；Unity Catalog 后端才是真正执行调用的地方，始终对发起调用的认证用户强制 UC 权限检查。

McpServer has three factory methods, and the two UC-specific ones save you from hand-building the URL: McpServer(url=...) takes a direct URL to any MCP endpoint; McpServer.from_uc_function(catalog, schema, function_name) builds /api/2.0/mcp/functions/{catalog}/{schema}/{function} automatically; McpServer.from_vector_search(catalog, schema, index_name) builds /api/2.0/mcp/vector-search/{catalog}/{schema}/{index}. A third backend exists alongside UC functions and AI Search: Genie spaces, reached at /api/2.0/mcp/genie/{space_id}, exposed as natural-language query tools — the same Genie mechanism File 10's Section F introduced via Genie One, now generalized to any Genie space a workspace has configured.

McpServer 有三个工厂方法，其中两个 UC 专用的能让你不用手动拼 URL：McpServer(url=...) 直接传一个 MCP 端点的 URL；McpServer.from_uc_function(catalog, schema, function_name) 自动拼出 /api/2.0/mcp/functions/{catalog}/{schema}/{function}；McpServer.from_vector_search(catalog, schema, index_name) 自动拼出 /api/2.0/mcp/vector-search/{catalog}/{schema}/{index}。除了 UC 函数和 AI Search，还有第三种后端：Genie 空间，走 /api/2.0/mcp/genie/{space_id}，以自然语言查询工具的形式暴露出来——这正是 File 10 Section F 里 Genie One 介绍过的那套 Genie 机制，这里推广到了一个 workspace 配置过的任意 Genie 空间。

D Multi-Agent Concepts

A single agent with tools is powerful, but many real workflows are better served by several specialized agents. The OpenAI Agents SDK's handoffs parameter (A1, above) is the native mechanism, and four things change once more than one agent is in the picture.

单个带工具的 agent 已经很强大了，但很多真实工作流更适合拆成几个专门化的 agent 来做。OpenAI Agents SDK 的 handoffs 参数（见上面 A1）就是原生机制，一旦场景里出现不止一个 agent，有四件事会发生变化。

Supervisor pattern: a supervisor agent receives every query and decides which worker to delegate to, using handoffs rather than calling tools directly — it reads each worker's name and instructions to pick the best fit. Worker specialization: each worker keeps a focused role, its own instructions, and its own small tool set, which keeps prompts concise and makes tool selection more accurate than one agent juggling many tools at once (e.g. a Data Analyst worker using classify_price_tier, a Business Analyst worker using neighborhood_summary). MCP-backed workers: each worker connects to its own McpServer instance scoped to only the UC function it needs, so it only ever sees tools relevant to its role — and the async with context manager has to wrap the entire multi-agent flow so every worker's MCP connection stays open for the full run, not just its own turn.

主管模式（Supervisor pattern）：一个主管 agent 接收所有请求，决定委托给哪个 worker，用的是 handoffs 而不是直接调工具——它读每个 worker 的名字和指令来判断谁最合适。Worker 专门化：每个 worker 都保持一个专注的角色、自己的指令、自己一小套工具，这样既能让 prompt 保持简洁，也比一个 agent 同时兼顾一大堆工具更能准确地选对工具（比如 Data Analyst worker 用 classify_price_tier，Business Analyst worker 用 neighborhood_summary）。MCP 支撑的 worker：每个 worker 连到自己专属的 McpServer 实例，只作用于它需要的那个 UC 函数，这样它就只会看到和自己角色相关的工具——而且 async with 这个上下文管理器要包住整个多 agent 流程，让每个 worker 的 MCP 连接在整次运行期间都保持打开，而不只是在轮到它说话的那一刻。

Distributed tracing: with only mlflow.openai.autolog(), each agent invocation produces its own independent trace — the supervisor call and each worker call show up as separate traces, making the overall orchestration hard to see. The fix is to wrap the entire multi-agent flow in one parent @mlflow.trace span; every child span (routing, each worker's LLM calls, each MCP tool call) then nests under that single root, producing one trace tree instead of several disconnected ones.

分布式追踪（Distributed tracing）：如果只用 mlflow.openai.autolog()，每一次 agent 调用都会产生各自独立的 trace——主管的调用和每个 worker 的调用会变成一堆彼此不相连的 trace，很难看清整体编排过程。解决办法是把整个多 agent 流程包在一个父级 @mlflow.trace span 里，之后每个子 span（路由、每个 worker 的 LLM 调用、每次 MCP 工具调用）都会挂在这同一个根节点下面，变成一棵完整的 trace 树，而不是好几棵互相断开的。

Advana / FM link

Supervisor-plus-specialized-workers is the shape a full cross-system FM Insight needs, exactly as flagged after File 9's single-vs-multi table: a supervisor routes an incoming FM question to a GFEBS specialist, a Navy ERP specialist, or an audit-evidence specialist, each scoped via its own McpServer to only the UC functions its own domain owns. That scoping is not just tidiness — it is a governance boundary. A GFEBS worker that can only reach GFEBS-scoped MCP tools cannot accidentally expose a Navy ERP function, even if the model hallucinates a reason to call it, because the tool was never in that worker's mcp_servers list to begin with.

主管加多个专门化 worker，正是 File 9 的单/多 agent 对比表之后就留下的那个判断：一个完整的跨系统 FM Insight 需要这个形状——主管 agent 把进来的财务问题路由给 GFEBS 专家、Navy ERP 专家，或者审计证据专家，每一个 worker 各自通过自己的 McpServer，只能访问自己领域拥有的那些 UC 函数。这种范围限定不只是整洁好看，它本身就是一道治理边界。一个 GFEBS worker 如果只能连到 GFEBS 范围内的 MCP 工具，就算模型出于某种"幻觉"出来的理由想调用 Navy ERP 的函数，也不可能意外地把它暴露出来，因为这个工具从一开始就没出现在这个 worker 的 mcp_servers 列表里。

E Other Supported Frameworks

This course focuses on the OpenAI Agents SDK, but Databricks supports several other agent-authoring frameworks. The one hard requirement for deployment, regardless of framework, is wrapping the agent with the MLflow ResponsesAgent interface.

这门课重点讲的是 OpenAI Agents SDK，但 Databricks 还支持好几个其他的 agent 开发框架。不管用哪个框架，部署时唯一硬性要求是：用 MLflow 的 ResponsesAgent 接口把 agent 包一层。

LangChain is the composable chains-and-tools framework. databricks-langchain provides ChatDatabricks (the model connection) and UCFunctionToolkit (UC functions as LangChain tools); create_agent from langchain.agents replaces the older AgentExecutor + create_tool_calling_agent pattern from LangChain 0.x; mlflow.langchain.autolog() gives automatic tracing. Note, though: Databricks now recommends MCP-based tools for most new agents — UCFunctionToolkit remains supported, not newly preferred.

LangChain 是那个可组合的链式/工具框架。databricks-langchain 提供 ChatDatabricks（连接模型）和 UCFunctionToolkit（把 UC 函数变成 LangChain 工具）；langchain.agents 里的 create_agent 取代了 LangChain 0.x 时代更老的 AgentExecutor + create_tool_calling_agent 这套模式；mlflow.langchain.autolog() 能自动打开 tracing。但要注意：Databricks 现在对大多数新 agent 推荐用基于 MCP 的工具——UCFunctionToolkit 仍然受支持，但已经不是新的首选了。

LangGraph is an open-source library for stateful, multi-actor LLM applications, defining agents as nodes in a directed graph with explicit state management and conditional edges — built for long-running workflows via its persistence/checkpointing features. On Databricks, create_agent (the same entry point as LangChain, since create_agent is built on LangGraph underneath) pairs with ChatDatabricks; MCP tools reach it through DatabricksMCPServer + DatabricksMultiServerMCPClient; mlflow.langchain.autolog() traces graph execution, capturing each graph step as a span.

F MLflow Integration

Traditional ML workloads are a single call: input in, output out, and the request/response pair is everything MLflow needs to capture. Agents are different in shape — multi-step, often looped — and the thing worth observing is not the call as a whole but each individual span: a span records when one unit of work started and ended, along with its metadata, inputs, and outputs. A full agent run is a trace: a tree of spans. MLflow Tracing captures this automatically for supported libraries (OpenAI SDK, LangChain, and others) and is designed to be compatible with the OpenTelemetry trace specification, so extra information like token counts is stored as key-value attributes on a span rather than as new top-level fields.

传统 ML 任务是一次调用：输入进去、输出出来，请求/响应这一对就是 MLflow 需要捕获的全部。Agent 的形状不一样——多步骤、常常是循环的——真正值得观察的不是整次调用，而是每一个独立的span（跨度）：一个 span 记录的是某一个工作单元什么时候开始、什么时候结束，以及它的元数据、输入、输出。一次完整的 agent 运行是一个trace（追踪）：一棵由 span 组成的树。MLflow Tracing 对支持的库（OpenAI SDK、LangChain 等）会自动完成这个捕获过程，而且设计上兼容 OpenTelemetry 的 trace 规范，所以像 token 数这样的额外信息，是作为 span 上的键值对"属性"存的，而不是新增一个顶层字段。

Spans nest hierarchically, mirroring execution: a parent span like "process user request" has child spans like "call retrieval tool" or "generate response" underneath it, with span relationships showing execution flow and span types (TOOL, CHAT_MODEL, RETRIEVER) categorizing what each one did. This hierarchy is exactly what distributed tracing (Section D) needs a single root span to produce — without a parent span wrapping the multi-agent flow, there is no tree, only several disconnected traces.

Span 是按层级嵌套的，映射的是真实的执行过程：一个像"处理用户请求"这样的父级 span，下面挂着像"调用检索工具"或者"生成回复"这样的子 span，span 之间的父子关系展示的就是执行流程，而 span 类型（TOOL、CHAT_MODEL、RETRIEVER）标明的是每一个 span 具体做了什么。这套层级结构，正是 Section D 里"分布式追踪"需要一个单一根 span 才能产生的东西——没有一个父级 span 把整个多 agent 流程包起来，就不会有一棵完整的树，只会有好几段互不相连的 trace。

Traces can be registered with Unity Catalog, not just MLflow's own experiment store: binding an experiment to a catalog/schema with a table_prefix writes every trace as governed Delta tables and SQL views. mlflow.set_experiment(experiment_name=..., trace_location=UnityCatalog(catalog_name="prod", schema_name="agents", table_prefix="oai_sa")) produces four Delta tables (oai_sa_otel_spans — one row per span, the call tree with timing and I/O; oai_sa_otel_logs — OpenTelemetry log records; oai_sa_otel_annotations — feedback and tags attached to traces; oai_sa_otel_metrics — metric data points) plus two SQL views built over them (oai_sa_trace_unified — full detail, one row per trace with spans, metadata, and assessments together; oai_sa_trace_metadata — fast filtering, tags and metadata only, no span payloads). This needs a SQL warehouse set via MLFLOW_TRACING_SQL_WAREHOUSE_ID. Once registered, the traces are governed (grants, lineage, audit), queryable with Databricks SQL, and readable programmatically with mlflow.search_traces().

Trace 不是只能存在 MLflow 自己的实验存储里，也可以注册进 Unity Catalog：把一个实验绑定到某个 catalog/schema，带上一个 table_prefix，之后每一条 trace 都会写成受治理的 Delta 表和 SQL 视图。mlflow.set_experiment(experiment_name=..., trace_location=UnityCatalog(catalog_name="prod", schema_name="agents", table_prefix="oai_sa")) 会产出四张 Delta 表（oai_sa_otel_spans——每个 span 一行，带时间和输入输出的调用树；oai_sa_otel_logs——OpenTelemetry 日志记录；oai_sa_otel_annotations——挂在 trace 上的反馈和标签；oai_sa_otel_metrics——指标数据点），再加两个建在这些表之上的 SQL 视图（oai_sa_trace_unified——全细节版，每条 trace 一行，span、元数据、评估结果都在一起；oai_sa_trace_metadata——快速过滤版，只有标签和元数据，不带 span 的完整载荷）。这需要通过 MLFLOW_TRACING_SQL_WAREHOUSE_ID 配一个 SQL 仓库。注册好之后，这些 trace 就是受治理的（授权、血缘、审计都有），可以用 Databricks SQL 查询，也可以用 mlflow.search_traces() 编程方式读取。

Advana / FM link — this answers a real FM Insight requirement, not just a debugging nicety

UC-registered MLflow traces solve a problem FM Insight will have regardless of which framework it ends up using: every agent decision that touches an audit-opinion-relevant number needs to be reconstructible later, the same way a GFEBS or Navy ERP transaction needs a traceable audit trail under A-123. A trace written to prod.agents.*_otel_spans is exactly that: which tool was called, with what arguments, returning what result, nested under which parent decision, queryable with ordinary Databricks SQL by an auditor who has never touched the agent's code. This is a stronger evidentiary artifact than a chat transcript, because it captures the tool calls and their actual arguments, not just the model's prose summary of what it did.

注册进 UC 的 MLflow trace，解决的是一个 FM Insight 不管最终选哪个框架都会遇到的问题：每一个碰到审计意见相关数字的 agent 决策，之后都得能被重新还原出来，就跟 GFEBS 或 Navy ERP 的一笔交易在 A-123 下需要有可追溯的审计轨迹一样。写进 prod.agents.*_otel_spans 的 trace 正好就是这个东西：调用了哪个工具、传了什么参数、返回了什么结果、挂在哪个父级决策下面，而且一个完全没碰过这个 agent 代码的审计人员，用普通的 Databricks SQL 就能查。这比一段聊天记录更有力的证据价值，因为它捕获的是实际的工具调用和真实参数，而不只是模型自己总结出来的一段"我做了什么"的文字描述。

With no parent span tying them together, each of those two calls becomes its own disconnected trace.

不带 MCP 跑一次 agent，会产生一个值得真正理解、而不只是记一笔的意外结果：一次 Runner.run() 调用会产生两条独立的顶层 trace，而不是一条。mlflow.openai.autolog() 是在 OpenAI 客户端这一层打补丁的，而一次典型的 agent 轮次底层通常会发生两次 LLM 调用——一次是模型推理这个问题、决定要调用 classify_price_tier，另一次是把工具返回的结果整理成最终的自然语言回答。没有一个父级 span 把这两次调用绑在一起，这两次调用就各自变成了互不相连的 trace。

Section D4 applies the fix by combining three things in one small function: McpServer.from_uc_function(...) builds the MCP connection for classify_price_uc specifically (not the whole schema — scoped to one function); the agent is redefined with mcp_servers=[mcp_server] in place of tools=[...], so it now discovers its tool at runtime through MCP rather than from an inline Python decorator; and the entire call is wrapped in @mlflow.trace(span_type="AGENT", name="data_analyst_mcp_execution"), an async def function using async with mcp_server: to open and close the MCP connection around the run. The decorator is what concatenates the MCP connection, the LLM calls, and the tool call into one unified trace instead of several disconnected ones — the same single-parent-span fix File 12's distributed-tracing discussion named for multi-agent flows, here solving the exact same problem for a single agent with two LLM calls per turn.

Section D4 用一个小函数把三件事合在一起，解决了这个问题：McpServer.from_uc_function(...) 专门为 classify_price_uc 这一个函数建好 MCP 连接（不是整个 schema——范围限定到一个函数）；agent 被重新定义，用 mcp_servers=[mcp_server] 取代了 tools=[...]，这样它现在是在运行时通过 MCP 发现工具，而不是靠内联的 Python 装饰器；整个调用被包在 @mlflow.trace(span_type="AGENT", name="data_analyst_mcp_execution") 里，是一个用 async with mcp_server: 来打开和关闭 MCP 连接的 async def 函数。真正把 MCP 连接、LLM 调用、工具调用串成一条统一 trace（而不是好几条互不相连的）的，就是这个装饰器——正是 File 12 讨论分布式追踪时提到的"单一父级 span"修复方式，这里用在了同一个问题上：一个单 agent 每轮要发生两次 LLM 调用的场景。

C Signatures, Modules, and the Adapter Round Trip

A signature is just an input/output contract. The shorthand form, "question -> answer: str", is enough for dspy.Predict, the simplest module, to work: qa = dspy.Predict(signature); qa(question=question). Swapping dspy.Predict for dspy.ChainOfThought with the identical signature adds a reasoning output field and an extra internal step, but — and this is the point of the exercise — the adapter round trip underneath stays exactly the same shape.

signature 说到底就是一个输入/输出的约定。简写形式，"question -> answer: str"，就足够让 dspy.Predict（最简单的 module）跑起来：qa = dspy.Predict(signature); qa(question=question)。用同一个 signature，把 dspy.Predict 换成 dspy.ChainOfThought，会多出一个 reasoning 输出字段和一个内部的额外步骤，但是——这正是这个练习要说明的事——底层那个 adapter 的来回流程，形状完全没变。

The course's own diagram walks one call through dspy.Predict in five numbered steps, worth carrying forward because it is the real mental model for everything DSPy does underneath a module: (1) you call qa(question="...") with keyword arguments named exactly by the signature; (2) the adapter's format() step writes a system message listing the input/output fields by name and type, and a user message marking the actual question under a [[ ## question ## ]] marker; (3) the LM itself only ever sees plain chat messages — it never sees your Python types, your Pydantic model, or the word "signature"; (4) the adapter's parse() step finds the [[ ## answer ## ]] marker in the reply and extracts the value, checking it against the declared output type; (5) you get back a typed Prediction object, pred.answer. ChatAdapter is the default adapter doing steps 2 and 4; swapping in JSONAdapter or TwoStepAdapter via dspy.configure(adapter=...) changes nothing about the program itself — the signature and the module code are untouched.

课程自己的图示，用五个编号步骤走了一遍 dspy.Predict 的一次调用，这个思路值得带走，因为它就是 DSPy 在任何一个 module 底下真正做的事：（1）你用跟 signature 里命名完全一致的关键字参数去调用 qa(question="...")；（2）adapter 的 format() 这一步，写出一条系统消息，按名字和类型列出输入/输出字段，再写一条用户消息，把真正的问题标在一个 [[ ## question ## ]] 标记下面；（3）LM 本身永远只看得到普通的聊天消息——它从来看不到你的 Python 类型、你的 Pydantic 模型，也看不到"signature"这个词；（4）adapter 的 parse() 这一步，在回复里找到 [[ ## answer ## ]] 这个标记，把值取出来，再拿声明好的输出类型去校验一下；（5）你拿到的是一个带类型的 Prediction 对象，pred.answer。ChatAdapter 是默认负责第 2、4 步的 adapter；用 dspy.configure(adapter=...) 把它换成 JSONAdapter 或者 TwoStepAdapter，程序本身一点都不用改——signature 和 module 的代码原封不动。
