6.3 One shared _lib, reused across all four course folders

Includes/_lib/ holds 22 Python modules: setup_orchestrator.py (48 KB, the generic installer), plus lakebase_setup.py, vector_search_manager.py, genie_creation.py, genie_deletion.py, agent_bricks_manager.py, product_data.py, spec_sheet_pdf_creation.py, and more. None of those last six are ever called by anything in this folder's config files — Folder 3's course content never touches Lakebase, vector search, Genie spaces, or Agent Bricks. They are dead code for this folder specifically, and that is the point once you see it: _lib is not Folder 3's own code. It is the same shared setup SDK copied unchanged into Folders 1, 2, 3, and 4, built generically enough to provision anything any of the four courses might need. Each course folder's own config-*.yaml files are what decide, at run time, which slice of _lib actually executes — Folder 1's configs turn on lakebase_setup and vector_search_manager because Folder 1 teaches Lakebase Search and AI Search; Folder 3's configs never mention either, so those modules just sit there unused.

Includes/_lib/ 里有 22 个 Python 模块：setup_orchestrator.py（48 KB，通用安装器），再加上 lakebase_setup.py、vector_search_manager.py、genie_creation.py、genie_deletion.py、agent_bricks_manager.py、product_data.py、spec_sheet_pdf_creation.py 等等。后面这六个，这个文件夹的任何配置文件都没有调用过——Folder 3 的课程内容完全不涉及 Lakebase、向量检索、Genie 空间或 Agent Bricks。看明白这一点之后就会发现：它们对这个文件夹来说是死代码，但这正是关键所在——_lib 根本不是 Folder 3 自己的代码，而是同一套共享的 setup SDK，原封不动地复制进了 Folder 1、2、3、4，写得足够通用，可以给这四门课里任何一门需要的东西做配置。真正决定运行时执行 _lib 里哪一部分的，是每个课程文件夹自己的 config-*.yaml——Folder 1 的配置会打开 lakebase_setup 和 vector_search_manager，因为 Folder 1 教的就是 Lakebase Search 和 AI Search；Folder 3 的配置从没提过这两个，所以这些模块就一直闲在那没人用。

6.4 Three config layers, one call per notebook

Every lesson notebook starts the same way: one %run or import into a Classroom-Setup script, which does exactly two things — install_libraries(config_path), then setup_demo_environment(config_path). Both read the same config-*.yaml file, and which one gets passed in depends on which notebook is calling. There are five config files for this folder: config-01.yaml (Module 1), config-02.yaml (Module 2's lectures/demos), config-02-lab.yaml (2.7's lab specifically — different learner catalog scope), config-03-lab.yaml (3.2's lab), and config-workspace-setup.yaml (the admin-only provisioning run). dependencies.toml sits one level further down: it is the actual package-version catalog (pyyaml 6.0.3, databricks-sdk 0.145.0, mlflow 3.16.1, …) that every config's libraries.groups list references by name instead of pinning a version inline — change a version once in dependencies.toml and every config that lists that package group picks it up.

每一个课程 notebook 的开头都长得一样：一句 %run 或 import 进一个 Classroom-Setup 脚本，这个脚本只做两件事——先 install_libraries(config_path)，再 setup_demo_environment(config_path)。两者读的是同一个 config-*.yaml 文件，具体传进去哪一个，取决于是哪个 notebook 在调用。这个文件夹一共有五个配置文件：config-01.yaml（Module 1）、config-02.yaml（Module 2 的讲课和演示）、config-02-lab.yaml（专门给 2.7 的 Lab 用——学员的 catalog 范围不一样）、config-03-lab.yaml（3.2 的 Lab）、config-workspace-setup.yaml（管理员专用的一次性配置运行）。dependencies.toml 还在更下面一层：它才是真正的包版本目录（pyyaml 6.0.3、databricks-sdk 0.145.0、mlflow 3.16.1……），每个 config 的 libraries.groups 列表都是按名字引用它，而不是把版本号直接写死在各自的配置里——只要在 dependencies.toml 里改一次版本号，所有引用了那个包分组的配置就都跟着更新。

This three-layer split — pinned dependencies once, per-office config files, one generic installer called the same way everywhere — is close to the exact shape FM Insight's own onboarding should take when a new DoW FM office comes onto the platform. One shared installer module per capability (a GFEBS connector, a Navy ERP connector, an audit-evidence retrieval module), one config file per office that turns on only what that office needs, and package versions pinned in exactly one place. The alternative — each office's onboarding getting its own hand-copied, slowly diverging setup script — is the thing this design is explicitly built to avoid, and it is also the thing most ad hoc DoD FM tooling actually does today.

这种三层拆分——依赖版本只钉一次、每个办公室一个配置文件、同一个通用安装器在哪都用同一种调用方式——跟 FM Insight 给国防部财务管理新办公室做平台接入时该用的形状，几乎一模一样。每种能力一个共享的安装模块（一个 GFEBS 连接器、一个 Navy ERP 连接器、一个审计证据检索模块），每个办公室一个只打开自己需要那部分的配置文件，包版本只在一个地方钉死。反过来的那种做法——每个办公室的接入脚本各自手抄一份、慢慢各走各的——正是这套设计刻意要避免的东西，而这恰恰也是今天大多数国防部财务管理临时拼凑出来的工具实际在做的事。

6.5 One shared agent, three consumers — and the one place that breaks the pattern

Includes/Workspace-Setup.py is an admin-only, run-once notebook. It creates the shared SF Airbnb listings table, three Unity Gateway model services (agent-model, judge-model, custom-judge-model), the two UC SQL tools, and — the key move — registers one tool-calling agent in Unity Catalog as dbacademy.agent_eval.airbnb@champion. Every learner's Classroom-Setup notebook then just loads that same registered model by alias; nobody builds their own copy of the Airbnb agent. The same registered model is also what agent-app/ (a real Databricks App, built on FastAPI + MLflow's AgentServer) serves as a live chat UI, and that app's thumbs-up/thumbs-down endpoint is what seeds the human-feedback data Module 3.2's lab reads. One agent, three consumers: every demo notebook, the deployed app, and the feedback lab.

Includes/Workspace-Setup.py 是一个只有管理员能跑、只跑一次的 notebook。它建好共享的旧金山 Airbnb 房源表、三个 Unity Gateway 模型服务（agent-model、judge-model、custom-judge-model）、两个 UC SQL 工具，最关键的一步——在 Unity Catalog 里注册一个会调用工具的 agent，命名为 dbacademy.agent_eval.airbnb@champion。之后每个学员的 Classroom-Setup notebook 只是按这个别名把同一个已注册模型加载进来；没有人会自己再搭一份 Airbnb agent。同一个注册模型，也正是 agent-app/（一个真正的 Databricks App，用 FastAPI + MLflow 的 AgentServer 搭的）用来提供实时聊天界面的那个东西，而这个 app 的点赞/点踩接口，正是 Module 3.2 的 Lab 要读取的人工反馈数据的来源。一个 agent，三个消费方：所有演示 notebook、部署出去的 app、以及反馈 Lab。

Module 2.7's lab is the one deliberate exception. Instead of loading the shared Airbnb agent, Classroom-Setup-02-Lab.py registers a different, learner-owned agent — nyc_taxi — built from Includes/agents/nyc_taxi_agent.py with its own tools in Includes/agent tools/nyc_taxi/ (calc_fare_est, trip_info, both UC SQL functions over samples.nyctaxi.trips). The lab needs a fresh, unevaluated agent for learners to practice evaluation on — sharing the already-evaluated Airbnb agent would defeat the point of the exercise.

Module 2.7 的 Lab 是故意安排的唯一例外。它不加载共享的 Airbnb agent，而是让 Classroom-Setup-02-Lab.py 注册一个不同的、学员自己的 agent——nyc_taxi——用 Includes/agents/nyc_taxi_agent.py 搭出来，自带工具放在 Includes/agent tools/nyc_taxi/（calc_fare_est、trip_info，都是基于 samples.nyctaxi.trips 的 UC SQL 函数）。这个 Lab 需要一个全新、还没被评测过的 agent 让学员练手；如果还用那个早就被评测过的 Airbnb agent，这个练习的意义就没了。

6.6 Includes/artifacts/ is a rebuilt copy, not a second source of truth

Includes/artifacts/evaluation_datasets/*.json and Includes/artifacts/nyc_taxi_agent.py look like duplicates of Includes/evaluation_datasets/*.json and Includes/agents/nyc_taxi_agent.py — and byte-for-byte, they almost are (a diff shows only a missing trailing newline). They are not a second, independently maintained source: _lib/artifacts_manager.py's ArtifactsManager class copies the real source files into Includes/artifacts/ fresh on every setup run, because that is the staging location the setup code then uploads to the learner's own Unity Catalog Volume (declared in config-01.yaml as volume_sources: [evaluation_datasets]). If you ever need to change one of these files, the one to edit is the source under Includes/evaluation_datasets/ or Includes/agents/ — never the copy under Includes/artifacts/, which gets overwritten the next time setup runs.

Includes/artifacts/evaluation_datasets/*.json 和 Includes/artifacts/nyc_taxi_agent.py 看起来像是 Includes/evaluation_datasets/*.json 和 Includes/agents/nyc_taxi_agent.py 的重复——逐字节对比下来，也几乎真是（diff 出来只差一个末尾换行符）。但它们不是第二份、各自独立维护的源文件：_lib/artifacts_manager.py 里的 ArtifactsManager 类，每次 setup 运行时都会把真正的源文件重新拷贝一份到 Includes/artifacts/，因为这是 setup 代码后续要上传到学员自己 Unity Catalog Volume 的暂存位置（config-01.yaml 里用 volume_sources: [evaluation_datasets] 声明）。如果以后要改这些文件里的某一个，该改的是 Includes/evaluation_datasets/ 或 Includes/agents/ 下面的源文件——绝不是 Includes/artifacts/ 下面那份拷贝，因为它下次 setup 一跑就会被重新覆盖。

6.7 automation/ is Databricks' own course-authoring QA, not learner material

Includes/automation/Configuration.py, qa_content_checker.py, and Test_All_Notebooks.py are not part of the lesson path at all — they are Databricks Academy's internal course-build tooling, included in the sync because it lives in the same workspace folder as the course. Test_All_Notebooks.py builds a single multi-task Lakeflow Job that runs every lesson notebook in dependency order, with a QA content checker running in parallel; qa_content_checker.py runs regex rules plus an LLM call (ai_query) over every content notebook to flag grammar, spelling, deprecated features, and manual UI steps a human still has to execute, writing its findings to a Delta table; Configuration.py is where the course's own test author points it at this specific course's name and lab notebook paths, with failure/success emails going to a Databricks engineer (aditya.baghel@databricks.com), not to any learner. None of it runs when you open a lesson notebook — it is the mechanism that validated the course before it ever reached you.

Includes/automation/Configuration.py、qa_content_checker.py、Test_All_Notebooks.py 根本不属于学习路径的一部分——它们是 Databricks Academy 自己内部用来构建课程的工具，之所以会同步进来，只是因为它们本来就放在跟课程同一个工作区文件夹里。Test_All_Notebooks.py 会建一个单独的、多任务的 Lakeflow Job，按依赖顺序跑完每一个课程 notebook，同时并行跑一个 QA 内容检查；qa_content_checker.py 对每一个内容 notebook 跑正则规则，外加一次 LLM 调用（ai_query），检查语法、拼写、过时功能，以及还需要人工去点的 UI 步骤，把结果写进一张 Delta 表；Configuration.py 就是课程作者自己填这门课的名字和 Lab notebook 路径的地方，失败/成功邮件发给的是一个 Databricks 工程师（aditya.baghel@databricks.com），不是发给任何学员。你打开一个课程 notebook 的时候，这些东西一个都不会运行——它是这门课在到你手上之前，用来验证自己的那套机制。

The regex-plus-LLM QA checker pattern here (deterministic rules for what can be checked mechanically, an LLM judge call for what can't, findings written to a queryable table) is the same shape Module 2's built-in and guideline judges teach — Databricks is literally dogfooding the course's own subject matter to build the course. That is a useful thing to point to when someone asks whether MLflow-judge-style evaluation is "real" production practice or a training exercise: the vendor runs this exact pattern on its own content pipeline.

这里的"正则加 LLM"质检模式（能机械检查的用确定性规则，不能机械检查的用一次 LLM 判断调用，结果写进可查询的表），跟 Module 2 教的内置判官和准则判官，是同一种形状——Databricks 其实是在用这门课自己讲的东西，反过来构建这门课本身。以后有人问 MLflow judge 这种评测方式到底是不是"真正的生产实践"还是只是教学练习，这是个很有用的例子：供应商自己的内容流水线，用的就是这一模一样的模式。

File 17 Lecture — The Challenge of Evaluating AI Agents

Duration: 15 minutes · why MLflow's evaluation framework exists in the first place

Big picture first: this lecture makes one argument. Traditional software testing asserts an exact output against a fixed input; AI agents break that model because the same input can legitimately produce different, equally-correct outputs, and the agent's own tool-and-reasoning decisions were never written down for anyone to assert against. The fix is not a better assertion — it is a different kind of check: a judge that evaluates whether a response is good, run continuously rather than once, against a deliberately-designed dataset. Everything in Folder 3 (built-in judges, guideline judges, custom judges, offline vs. online strategy) is a specific answer to the problem this lecture states in the abstract.

先说大图景：这节课只讲一个论点。传统软件测试是拿一个固定输入去断言一个精确输出；AI agent 把这套模型打破了，因为同一个输入完全可能合理地产生不同、但同样正确的输出，而且 agent 自己做的工具调用和推理决策，从一开始就没人写下来过，没法拿去断言。解决办法不是把断言写得更精细，而是换一种完全不同的检查方式：用一个"判官"去判断一个回答好不好，而且要持续不断地跑，而不是跑一次就完事，跑在一个经过刻意设计的数据集上。Folder 3 后面的内容——内置判官、准则判官、自定义判官、离线 vs. 线上策略——都是对这节课抽象提出的这个问题，给出的具体答案。

A Why Traditional Testing Falls Short

A1. Traditional software testing relies on deterministic inputs and expected outputs: unit, integration, and end-to-end tests that verify the exact same result every time given the same input. A2. AI agents break every leg of that paradigm at once — not just the output, but behavior, context, verification, and edge cases.

A1. 传统软件测试依赖的是确定性的输入和预期输出：单元测试、集成测试、端到端测试，验证的是同一个输入每次都产出完全一样的结果。A2. AI agent 把这套范式的每一条腿都一次性打断了——不只是输出，行为、上下文、验证方式、边界情况全都变了。

How AI agents break the deterministic testing paradigm, from the course's own comparison table
Traditional softwareAI agents

Why exact matching fails

An agent answering "What's the weather in San Francisco?" might say "It's currently 65°F and sunny," "San Francisco weather: 65 degrees, clear skies," or "The temperature in SF is 65°F with no clouds." All three are correct and helpful. None match exactly — assert output == "expected_response" fails on all three.

一个 agent 回答"旧金山天气怎么样"，可能说"现在 65 华氏度，晴天"，也可能说"旧金山天气：65 度，天空晴朗"，或者"旧金山气温 65 华氏度，没有云"。三个回答都正确、都有帮助。但三个字符串没有一个完全一样——assert output == "expected_response" 三个都会判定失败。

B The Agent Evaluation Challenge

B1. Multi-dimensional complexity. Agent evaluation has to assess not just the final answer but the quality of intermediate steps: multi-step reasoning (did the chain of tool calls and retrievals make sense, not just the final sentence), tool-calling accuracy (right tool, right parameters, correctly interpreted results), and retrieval quality for RAG-based agents (relevant documents, correctly synthesized across sources).

B1. 多维度的复杂性。评测 agent 不能只看最终答案，还得看中间每一步的质量：多步推理（一连串工具调用和检索串起来是不是讲得通，而不只是看最后一句话）、工具调用是否准确（工具选对没有、参数传对没有、结果有没有正确解读）、以及（对基于 RAG 的 agent 而言）检索质量（检索到的文档相不相关、有没有把多个来源正确地综合起来）。

B2. Safety and real-world variability. Agents must avoid harmful outputs, respect boundaries, and decline inappropriate requests — qualities that need judgment, not a pass/fail assertion. Production agents also meet diverse queries, unexpected phrasings, and edge cases that are hard to anticipate during development. Both demand an evaluation framework built for the probabilistic, contextual nature of agents, not one borrowed from deterministic software.

B2. 安全性和真实世界的多变性。Agent 必须避免有害输出、尊重边界、拒绝不合适的请求——这些特质需要判断力，不是一个非黑即白的断言能解决的。生产环境里的 agent 还会遇到各种各样的问法、意料之外的表达方式，以及开发阶段很难预料到的边界情况。这两条都要求一套专门为 agent 的概率性、上下文依赖性设计的评测框架，而不是直接照搬确定性软件那一套。

C Evaluation as a Continuous Process

C1. Unlike traditional software, where a stable test suite is a one-time quality signal, agent evaluation runs on a cycle: rapid evaluation during development, comprehensive validation pre-deployment, continuous monitoring in production, and new failure cases from production feeding back into the evaluation dataset — which then re-enters development. C2. That cycle only works if the evaluation infrastructure is scalable, automated, and built into the development workflow from the start, not bolted on before a release.

C1. 和传统软件不一样——传统软件的测试套件是一次性建好、长期当作质量信号——agent 评测跑的是一个循环：开发阶段快速评测，上线前做全面验证，生产环境持续监控，生产里出现的新失败案例再反过来喂回评测数据集，然后重新进入开发阶段。C2. 这个循环只有在评测基础设施从一开始就是可扩展、自动化、嵌进开发流程里的时候才真正跑得起来，而不是等到快发布了才临时加上去。

D Preparing for Evaluation

D1. Before using any evaluation framework, make evaluation both purposeful and reproducible: define quality dimensions, assemble a representative dataset, and enable tracing so judges can assess how an answer was produced, not only the answer itself. D2. The dataset has three parts, only one of which is required.

D1. 在用任何评测框架之前，先让评测变得有目的、可复现：定义清楚要评测的质量维度、搭好一个有代表性的数据集、打开 tracing，让判官不仅能看答案本身，还能看这个答案是怎么产生的。D2. 数据集有三个部分，其中只有一个是必须的。

D2 key principles: representativeness (common, high-impact queries so offline results generalize), edge cases (ambiguous, out-of-scope, adversarial prompts to surface failure modes early), diversity (length, complexity, domain, user expertise), ground truth and/or guidelines (expected facts for objective questions, natural-language guidelines where style or policy matters), and storage/versioning (MLflow evaluation datasets live in Unity Catalog, with built-in versioning, lineage, sharing, and governance). D3 operational setup: track with MLflow experiments and runs (stable names, tags for agent and dataset versions); govern with Unity Catalog (access control, versioning, lineage, registered agents for end-to-end traceability); learn from production (log deployed-agent traces to an experiment, mine user feedback for new evaluation examples).

D2 关键原则：代表性（常见、高影响力的查询，让离线结果能推广到生产环境）、边界情况（模糊的、超出范围的、对抗性的提示，提早暴露失败模式）、多样性（长度、复杂度、领域、用户熟练程度都要有变化）、真值和/或准则（客观问题用预期事实，风格或政策相关的问题用自然语言准则）、存储和版本管理（MLflow 的评测数据集存在 Unity Catalog 里，自带版本管理、血缘、共享和治理）。D3 运行层面的搭建要求：用 MLflow 的 experiment 和 run 做追踪（稳定的命名、给 agent 和数据集版本打标签）；用 Unity Catalog 做治理（访问控制、版本管理、血缘追踪、注册 agent 以实现端到端可追溯）；从生产环境里学习（把部署出去的 agent 的 trace 记录到一个 experiment 里，挖掘用户反馈，补充新的评测样例）。

File 19 Lecture — MLflow's Evaluation Framework

Duration: 20 minutes · the architecture every later file in Folder 3 is built on top of — last file in Module 1

Big picture first: File 17 argued, in the abstract, that agents need a different kind of testing. File 19 is where that abstraction becomes an actual architecture: three inputs (a dataset, scorers, a predict function) flow into one orchestration point, mlflow.genai.evaluate(), which calls the agent, traces every call, runs the scorers, and logs a result you can query two ways — aggregated metrics, or per-row assessments sitting on each trace. Tracing is not a side feature of this architecture; it is load-bearing, because several judges literally cannot score an answer without reading the trace of how that answer was produced. Everything in Modules 2 and 3 — built-in judges, guideline judges, custom judges, offline vs. online strategy — is a variation on filling in one of these three inputs or reading one of these two outputs. This is the single most important file to hold firmly in memory for the rest of Folder 3.

先说大图景：File 17 在抽象层面论证了 agent 需要一种不同的测试方式。File 19 就是这个抽象变成一套实际架构的地方：三个输入（一个数据集、一组判官、一个 predict 函数）汇入同一个编排点——mlflow.genai.evaluate()——它会调用 agent、给每次调用打 trace、跑判官、把结果记录下来，而这个结果你可以用两种方式查：汇总指标，或者挂在每条 trace 上的逐行评估结果。Tracing 在这套架构里不是一个可有可无的附加功能，它是承重的——因为有几种判官，没有 trace 根本没法判断一个答案是怎么产生的，也就没法打分。Module 2 和 Module 3 里的一切——内置判官、准则判官、自定义判官、离线 vs. 线上策略——本质上都是在填这三个输入里的某一个，或者读这两种输出里的某一个的变体。这是整个 Folder 3 里最重要的一个文件，后面全靠它。

A MLflow for Agent Evaluation

A1. Five MLflow capabilities carry the weight of agent evaluation: tracing, scorers and judges, mlflow.genai.evaluate(), evaluation experiments for comparing runs, and production monitoring. A detail worth keeping for D5-style exam questions: MLflow traces are fully OpenTelemetry-compatible, so they can export to Datadog, Grafana, or Splunk via MLflow-only, OTel-only, or dual export — evaluation data is not trapped inside MLflow's own UI.

A1. 五项 MLflow 能力撑起了整个 agent 评测：tracing、判官（scorers and judges）、mlflow.genai.evaluate()、用来对比多次运行的 evaluation experiments，以及生产监控。有一个细节值得记下来，考 D5 类题目时可能用到：MLflow 的 trace 完全兼容 OpenTelemetry，可以通过"只走 MLflow"、"只走 OTel"或"两边都导出"三种方式，导出到 Datadog、Grafana 或 Splunk——评测数据不会被锁死在 MLflow 自己的界面里。

B Core Architecture — Three Fundamental Components

B1. Three components flow into mlflow.genai.evaluate(): the evaluation dataset (what to test — inputs required, outputs and expectations optional, as laid out in File 17's D2/D3), scorers (how to grade — built-in, guideline, custom, or code-based), and the predict function (how to call the agent — optional if the data already holds pre-generated outputs, the "answer sheet" mode). evaluate() calls the agent for each row, traces every call, runs each scorer, and logs the run; it returns an EvaluationResult with a run_id and aggregated metrics, with per-row assessments living on each row's trace.

B1. 三个组件汇入 mlflow.genai.evaluate()：评测数据集（测什么——inputs 必须，outputs 和 expectations 可选，跟 File 17 的 D2/D3 讲的一致）、判官（怎么打分——内置、准则、自定义，或基于代码）、predict 函数（怎么调用 agent——如果数据里已经有预先生成好的输出，这个可以省略，也就是"答案卷"模式）。evaluate() 会对每一行调用 agent，给每次调用打 trace，跑每个判官，把这次运行记录下来；返回一个 EvaluationResult，带一个 run_id 和汇总指标，逐行的评估结果则挂在每一行的 trace 上。

C The mlflow.genai.evaluate() Function

C1. Central orchestration point. evaluate() is an evaluation harness: feed in test data, run the app, automatically score the results. It connects offline testing with production monitoring — the same evaluation logic used in development can also run in production (the thread File 19 E and File 27 pick up).

C1. 中央编排点。evaluate() 是一个评测框架：喂进去测试数据，跑你的应用，自动打分。它把离线测试和生产监控连起来——开发阶段用的那套评测逻辑，同样可以在生产环境里跑（这条线 File 19 的 E 部分和 File 27 会接着讲）。

C2. Key parameters. data — rows of inputs plus optional outputs/expectations: a list of dicts, a DataFrame, or a Unity Catalog evaluation dataset. predict_fn — called once per row with that row's inputs; omit it to score outputs already present in the data. When provided, it must accept keys from inputs as keyword arguments, return a JSON-serializable dict, be instrumented with MLflow Tracing, and emit exactly one trace per call. scorers — built-in, guideline, custom, and code scorers; each judge's model is itself a Unity Gateway model service. The return value — an EvaluationResult with run_id and aggregated metrics — is the fourth part of the same picture.

C2. 关键参数。data——每一行是输入，加上可选的 outputs/expectations：可以是一个 dict 列表、一个 DataFrame，或者一个存在 Unity Catalog 里的评测数据集。predict_fn——每一行调用一次，传入这一行的 inputs；如果数据里已经有现成的输出，这个参数可以省略不写。如果写了，它必须接受 inputs 字典里的键作为关键字参数，返回一个可以 JSON 序列化的 dict，要用 MLflow Tracing 打上标记，并且每次调用正好产生一条 trace。scorers——内置、准则、自定义、代码判官都算；每个判官背后的模型本身也是一个 Unity Gateway 模型服务。返回值——一个带 run_id 和汇总 metrics 的 EvaluationResult——是这张图的第四块拼图。

C3 Evaluation Workflow

Five steps, in order, every time evaluate() runs: (1) load the data and validate its structure; (2) generate outputs by calling predict_fn for each row — skipped when the data already has outputs; (3) create traces, with each call traced automatically; (4) run the scorers on every row; (5) aggregate and log the metrics and results to MLflow.

每次跑 evaluate()，都是这五步，顺序不变：（1）加载数据并校验结构；（2）对每一行调用 predict_fn 生成输出——如果数据里已经有输出，这一步跳过；（3）创建 trace，每次调用都自动打上 trace；（4）对每一行跑判官；（5）把指标和结果汇总，记录到 MLflow。

C4 Return Value and Results Access

The function returns an EvaluationResult with run_id, metrics (aggregated dict), artifacts, and tables (per-example DataFrames). In MLflow 3, per-example results are read from the traces, not from the result object directly: mlflow.search_traces(run_id=results.run_id, return_type="list"), then iterate trace.info.assessments for each scorer's name and value. The course's own mock run makes this concrete: aggregated metrics correctness/mean 0.80, safety/mean 1.00, tone/mean 0.60, and a per-row table where one row — "What is the average listing price in Haight Ashbury?" — fails correctness specifically because the agent said 92.40 against an expected 87.71, with the rationale attached directly to that cell.

返回的 EvaluationResult 带 run_id、metrics（汇总字典）、artifacts，以及 tables（逐行 DataFrame）。在 MLflow 3 里，逐行结果不是直接从返回对象里读，而是从 trace 里读：mlflow.search_traces(run_id=results.run_id, return_type="list")，然后遍历每条 trace 的 trace.info.assessments，拿到每个判官的名字和打分。课程自己的模拟运行把这个过程讲得很具体：汇总指标 correctness/mean 0.80、safety/mean 1.00、tone/mean 0.60，逐行表格里有一行——"Haight Ashbury 的平均房价是多少"——专门因为 correctness 判官不通过而"失败"，原因是 agent 给出的答案是 92.40，而预期是 87.71，这个理由就直接挂在那个格子上。

D MLflow Tracing — the Foundation of Agent Observability

D1. Tracing captures every step of the agent's reasoning: model calls (prompts, responses, parameters), tool invocations (inputs and return values), retrieval operations (documents and metadata), the duration of every operation, and the parent-child hierarchy tying them together. Tracing is enabled automatically when using evaluate() with a properly instrumented predict_fn.

D1. Tracing 会记录 agent 推理过程中的每一步：模型调用（提示、回复、参数）、工具调用（输入和返回值）、检索操作（文档和元数据）、每个操作的耗时，以及把这些都串起来的父子层级关系。只要 predict_fn 打好了标记，用 evaluate() 跑的时候 tracing 会自动打开。

D3 Why Tracing Matters for Evaluation

Some judges, like RetrievalSufficiency, literally cannot function without a trace — they analyze what was retrieved, not just the final response, so without traces these evaluations would be impossible. Tracing also enables debugging by letting you inspect exactly what happened during a failed evaluation: was it retrieval quality, tool selection, or LLM reasoning that broke?

有些判官，比如 RetrievalSufficiency，没有 trace 根本没法工作——它分析的是检索到了什么，不只是最终回复，所以没有 trace 这类评测是做不了的。Tracing 还能帮你调试：评测失败的时候，你能准确看到当时发生了什么——到底是检索质量、工具选择，还是 LLM 推理的问题。

E Production Monitoring and Unity Gateway

Evaluation doesn't stop at deployment — the same MLflow pieces cover a deployed agent too. The deployed agent (File 18's agent-app, built on AgentServer) logs a trace for every request to its own MLflow experiment, and user feedback captured through the app's /api/feedback endpoint is saved on those same traces. And every model call — from the agent and from the judges alike — goes through a Unity Gateway model service, so permissions, rate limits, and usage tracking apply uniformly to both. Failures found in production become new rows in the evaluation dataset, closing the loop File 17's C1 described; File 27's Offline vs. Online Evaluation Strategies lecture walks through exactly that loop.

评测不会在部署那一刻就结束——同一套 MLflow 组件，照样覆盖一个已经部署出去的 agent。部署出去的 agent（File 18 里那个基于 AgentServer 搭的 agent-app）会把每一次请求的 trace，记录到它自己的 MLflow experiment 里，用户通过 app 的 /api/feedback 接口给出的反馈，也保存在同一批 trace 上。离线用的那些判官，也可以注册成自动跑在生产 trace 抽样上，用 .register() 和 .start()。而且每一次模型调用——不管是 agent 自己，还是判官——都要经过一个 Unity Gateway 模型服务，所以权限、速率限制、用量追踪，对两边都是统一适用的。生产环境里发现的失败案例，会变成评测数据集里的新一行，正好接上 File 17 的 C1 讲的那个闭环；File 27 的"离线 vs. 线上评测策略"那节课，会完整讲一遍这个闭环。

A Judge Types Overview — the Evaluation Judge Spectrum

A1. Three LLM-judge types, in increasing order of customization: built-in judges (out of the box — research-validated judges like Correctness and Safety for a quick quality baseline), guideline judges (natural language — pass/fail rules you write in plain English with Guidelines, for tone/policy/style), and custom LLM judges (fully custom — your own instructions and output type with make_judge(), for domain-specific quality). Two non-LLM scorer types sit alongside them: code-based scorers (deterministic Python checks with @scorer, no LLM call — exact match, format validation, latency) and third-party scorers (external metrics from open-source evaluation frameworks your team already trusts).

A1. 三种 LLM 判官，按"定制程度"从低到高排列：内置判官（开箱即用——像 Correctness、Safety 这种经过研究验证的判官，拿来做一个快速的质量基线）、准则判官（自然语言——用 Guidelines 写成的、用普通英文表达的通过/不通过规则，适合语气、政策、风格这类要求）、自定义 LLM 判官（完全定制——用 make_judge() 写自己的指令和输出类型，适合特定领域的质量判断）。另外还有两种不靠 LLM 的判官：代码判官（用 @scorer 装饰的确定性 Python 检查，不调用 LLM——精确匹配、格式校验、延迟检查）和第三方判官（来自开源评测框架、团队已经信任的外部指标）。

File 22 Lecture — Guideline Judges

Duration: 10 minutes · when "factually correct" isn't the question — tone, policy, formatting

Big picture first: File 20's table showed Correctness needs expectations.expected_facts — ground truth that is objectively checkable. Guideline judges answer a different question: what about requirements that aren't facts at all, but rules — "must be professional," "must mention the 30-day window," "must not use slang"? The move is to let a domain expert write the rule in plain English instead of asking an engineer to encode it, and then split that idea in exactly two directions: one rule applied uniformly to every row, or a different rule per row.

先说大图景：File 20 的表里讲过，Correctness 需要 expectations.expected_facts——这是可以客观核查的真值。准则判官要回答的是另一个问题：那些根本不是"事实"、而是"规则"的要求怎么办——"必须专业"、"必须提到 30 天这个期限"、"不能用俚语"？解决办法是让业务专家直接用普通英文写规则，不用让工程师把它翻译成代码，然后把这个想法朝两个方向各展开一种：同一条规则套用到每一行，或者每一行用不同的规则。

A Two Types of Guideline Judges

A1. Guidelines() applies the same rules to every row — ideal for tone, style, formatting, and compliance that should hold uniformly across the whole dataset. ExpectationsGuidelines() applies different rules per example, read from each row's own expectations.guidelines field — ideal for scenario-specific criteria that genuinely differ row to row.

A1. Guidelines() 把同一套规则套用到每一行——适合语气、风格、格式、合规性这类应该在整个数据集上统一生效的要求。ExpectationsGuidelines() 每个例子用不同的规则，从每一行自己的 expectations.guidelines 字段里读——适合那些真的是逐行不同的场景化标准。

Global: Guidelines(name="professional_tone", guidelines=["The response must use professional language", "The response must not use slang", "The response must address the user respectfully"], model="databricks:/catalog.schema.judge-model"), passed to scorers=[tone_guidelines] once for the whole run. Per-row: each record carries its own rules inside expectations.guidelines — e.g. a refund-policy row requiring the response mention the 30-day window and the receipt requirement, a support-contact row requiring a contact method and conciseness — and the scorer is instantiated with no arguments at all: scorers=[ExpectationsGuidelines()], since the rules travel with the data, not the judge.

B Advantages and Best Practices

B1. Why guideline judges. Accessible to experts (domain experts write rules without coding), fast to iterate (change a rule without changing code), interpretable (the rules document what you expect, in plain language anyone can read), and flexible (rules capture complex, context-dependent requirements that a code-based scorer can't express cleanly).

B1. 为什么要用准则判官。对专家友好（业务专家不用写代码就能写规则）、迭代快（改规则不用改代码）、可解释（规则本身就用普通语言写清楚了你期望什么，谁都能看懂）、灵活（能表达代码判官很难干净表达的那种复杂、依赖上下文的要求）。

B2. Writing effective guidelines — the one rule that matters most: refer to inputs as "the request" and outputs as "the response," because the LLM judge automatically extracts request/response data from the trace using exactly that vocabulary. Recommended phrasing: "The response must …" (required), "The response must not …" (prohibited), "The response may optionally …" (suggested, not required). Be specific and concrete — "the response must cite the source document" beats "the response should be credible" — write guidelines that can be objectively verified, focus on observable attributes, leave as little ambiguity as possible, and test each guideline against multiple examples before trusting it.

B2. 怎么写好的准则——最关键的一条规则：把输入称为"the request"，把输出称为"the response"，因为 LLM 判官会用正好这套词汇，从 trace 里自动抽取 request/response 数据。推荐的措辞方式："The response must …"（必须）、"The response must not …"（禁止）、"The response may optionally …"（建议但不强制）。要具体、要能落地——"回复必须引用来源文档"比"回复应该让人觉得可信"要好得多——写的准则要能被客观验证，聚焦在可观察的属性上，尽量减少歧义，而且在信任一条准则之前，先拿多个例子测一遍。

The vocabulary trap

Writing a guideline as "the question must be clear" instead of "the request must be clear" isn't a style nitpick — it can silently fail to bind to the trace data the judge is actually extracting. The request/response vocabulary is a hard requirement, not a suggestion.

把准则写成"这个问题必须清楚"而不是"the request must be clear"，不只是用词习惯的问题——它可能会悄无声息地没对上判官实际从 trace 里抽取的数据。request/response 这套词汇是硬性要求，不是建议。

File 24 Lecture — Custom Judges and Feedback

Duration: 10 minutes · the bottom of File 20's judge spectrum — full control, both deterministic and LLM-based

Big picture first: this file closes out File 20's spectrum from the two custom ends — code-based scorers (@scorer, deterministic, no LLM) and custom LLM judges (make_judge(), your own instructions and output type) — and then names the one structure every judge type in Folder 3, built-in through custom, actually returns: a Feedback object with a value, a rationale, and metadata. The rationale is not decoration; it is the reason a judge's output is debuggable at all.

先说大图景：这个文件从两个"完全自定义"的方向，把 File 20 的判官谱系收尾——代码判官（@scorer，确定性，不调用 LLM）和自定义 LLM 判官（make_judge()，自己写指令和输出类型）——然后点出一个事实：从内置判官到自定义判官，Folder 3 里每一种判官类型实际返回的，都是同一种结构：一个带 value、rationale、metadata 的 Feedback 对象。Rationale 不是装饰性的东西；它是让判官的输出能够被调试的根本原因。

A Code-Based Scorers

A1. The @scorer decorator converts a Python function into a reusable evaluation component. The function can accept any combination of inputs (dict — the app's raw input), outputs (any — the app's raw output), expectations (dict — ground truth), and trace (the complete mlflow.entities.Trace, every span and metadata). This is the imperative approach: evaluation logic written directly in Python, full control over scoring, data access, and error handling — use it when criteria are expressible as deterministic code (format checks, length validation, keyword matching, schema verification).

A1. @scorer装饰器把一个 Python 函数变成一个可复用的评测组件。这个函数可以接受 inputs（dict——应用的原始输入）、outputs（任意类型——应用的原始输出）、expectations（dict——真值）、trace（完整的 mlflow.entities.Trace，所有 span 和元数据）这几个参数的任意组合。这是"命令式"的方式：评测逻辑直接用 Python 写出来，打分、数据访问、错误处理全都由你自己完全掌控——适合那种能写成确定性代码的标准（格式检查、长度校验、关键词匹配、schema 校验）。

Two return styles: with a Feedback object — Feedback(value="yes", rationale=f"Response length ({word_count} words) is appropriate") — gives full interpretability, you can see why a row passed or failed; or a primitive return — just return "yes" if 20 <= wc <= 100 else "no" — more concise for straightforward pass/fail, but with no rationale for the decision.

两种返回方式：返回一个 Feedback 对象——Feedback(value="yes", rationale=f"Response length ({word_count} words) is appropriate")——能完全解释清楚，你能看到为什么某一行通过或不通过；或者返回一个基本值——直接 return "yes" if 20 <= wc <= 100 else "no"——对简单的通过/不通过判断更简洁，但没有任何理由说明这个判断是怎么来的。

B Custom LLM Judges

B1. When to use them. Domain-specific criteria unique to the application, nuanced assessments beyond what built-in judges capture, proprietary standards such as regulations and compliance rules, and multi-signal logic that combines several data sources.

C Feedback Objects and Rationales

C1. Every MLflow judge — built-in, guideline, code-based, or custom LLM — returns a structured Feedback object, never a bare scalar underneath. C2. Why rationales matter. Debugging — see why a response failed, not just that it failed. Communication — explain results to stakeholders who weren't in the room for the evaluation design. C2. 为什么 rationale 很重要。调试——能看到一个回复为什么失败，不只是知道它失败了。判官验证——核查判官自己的推理是不是合理，不只是看结论对不对。找规律——rationale 里反复出现的主题，指向的是系统性的问题，不是一次性的偶然失败。沟通——向那些没参与评测设计的相关人员解释评测结果。实际工作流：读所有失败案例的 rationale 找规律，抽查通过案例的 rationale 确认判官的推理是真的合理（不是蒙对了），从常见的 rationale 措辞里提炼出失败类型的分类，在跟团队讨论评测结果时分享有代表性的 rationale。

File 27 Lecture — Offline vs. Online Evaluation Strategies

Duration: 20 minutes · "Module 3 - Custom Judges and Human Feedback" in the actual folder — this file closes the offline side and opens onto File 28's human-feedback lab

Big picture first: every evaluation run so far in Folder 3 has been offline — a curated dataset, run once, scored, done. This file names that as half the picture and builds the other half: production monitoring, where the same judges run continuously on live traffic. The real content isn't either half alone, it's the loop between them — production failures become new offline test cases, and only agents that already passed offline get shipped to produce that traffic in the first place.

先说大图景：到目前为止 Folder 3 里跑过的每一次评测，都是离线的——一个精心整理的数据集，跑一次，打分，完事。这个文件指出这只是半张图，然后把另一半补上：生产监控，同一批判官在真实流量上持续运行。真正的内容不是这两半各自是什么，而是它们之间的那个循环——生产环境里的失败案例变成新的离线测试用例，而只有已经通过离线评测的 agent，才有资格先上线去产生这些流量。

A Evaluation Strategy Overview — Two Complementary Approaches

A1. Offline (before deployment, curated datasets): curate a dataset of use cases and edge cases, run the agent on every row, score each response with judges, gate the release on the results — controlled and reproducible. Online (in production, real user traffic): trace every production request, score a sample of traces automatically, collect user feedback on answers, monitor quality and alert on drops — real-world and continuous. The version that passed offline ships; failures in production flow back as new offline test cases, closing the loop.

A1. 离线（部署之前，精心整理的数据集）：整理一个覆盖常见用例和边界情况的数据集，对每一行跑 agent，用判官给每个回复打分，根据结果决定是否放行发布——可控、可复现。线上（生产环境，真实用户流量）：给每一次生产请求都打上 trace，自动给一部分 trace 打分，收集用户对答案的反馈，监控质量并在下降时报警——贴近真实、持续不断。离线评测通过的版本才会上线；生产环境里的失败案例会反过来变成新的离线测试用例，把这个循环闭合起来。

B Offline Evaluation — Pre-Deployment Validation

B1. Five steps: curate a dataset of common use cases and edge cases; define expectations (optional ground truth or guidelines); run the agent to generate responses; apply scorers across every response; analyze and iterate by comparing results across runs. Strengths: rigorous validation before users ever see the agent, A/B testing different configurations, baseline metrics for production. Limitations: may not fully represent real user behavior, static datasets go stale, can't capture scale or diversity issues that only show up with real traffic.

B1. 五步：整理一个覆盖常见用例和边界情况的数据集；定义 expectations（可选的真值或准则）；跑 agent 生成回复；对每个回复应用判官；通过对比多次运行的结果来分析和迭代。优势：在用户见到 agent 之前就做了严格的验证、可以 A/B 测试不同的配置、能给生产环境提供基线指标。局限：可能没法完全代表真实用户的行为、静态数据集会过时、没法捕捉到只有在真实流量下才会出现的规模或多样性问题。

C Online Evaluation — Production Monitoring

C1. Five steps: deploy with tracing so every production request is traced (in this course, the Airbnb assistant app logs a trace per request to its MLflow experiment); capture traces in that experiment; score automatically by registering scorers and starting them with .register() and .start(); alert and collect feedback to monitor quality; augment the dataset with production examples. Supported scorer types for production monitoring: built-in judges, make_judge(), Guidelines, and @scorer-decorated functions all work — only direct Scorer subclasses and third-party scorers are excluded. Production monitoring capabilities: auto scoring (LLM judges run on production traces), sampling (configurable rates), alerting (when quality drops below a threshold), and trace inspection (deep dives into failures). Strengths: reflects actual user experience, detects unanticipated issues, generates data for continuous improvement. Limitations: users may hit failures first, root-cause attribution is harder, requires production infrastructure.

C1. 五步：部署时带上 tracing，让每一次生产请求都被追踪（这门课里，Airbnb assistant app 会把每次请求的 trace 记录到它的 MLflow experiment）；把 trace 捕获到那个 experiment 里；通过注册判官、用 .register() 和 .start() 启动它们，实现自动打分；通过报警和收集反馈来监控质量；用生产环境的真实案例扩充数据集。生产监控支持的判官类型：内置判官、make_judge()、Guidelines、@scorer 装饰的函数都可以用——只有直接继承 Scorer 的子类和第三方判官不行。生产监控的能力：自动打分（LLM 判官跑在生产 trace 上）、采样（可配置采样率）、报警（质量低于某个门限时触发）、trace 检查（深入排查失败案例）。优势：反映真实的用户体验、能发现没预料到的问题、为持续改进提供数据。局限：用户可能先遇到失败、根因定位更难、需要生产环境的基础设施支撑。

D Complementary Strategies

D1. Offline is for quality gates (pre-deployment validation), A/B testing (comparing implementations side by side), hypothesis testing ("does the new prompt reduce hallucinations?"), and rapid iteration (fast feedback during development). Online is for generalization checks (do offline results actually hold in production?), drift detection (catching performance degradation over time), user insight (real needs, pain points, edge cases), and dataset mining (building evaluation datasets from actual usage).

D1. 离线评测适合：质量门槛（部署前的验证）、A/B 测试（并排比较不同实现）、假设检验（"新的 prompt 能不能减少幻觉？"）、快速迭代（开发过程中的快速反馈）。线上评测适合：泛化检验（离线的结果在生产环境里到底站不站得住）、漂移检测（捕捉随时间推移的性能下降）、用户洞察（真实的需求、痛点、边界情况）、数据集挖掘（从真实使用情况里构建评测数据集）。

D2. Creating a feedback loop. The course's own swimlane walks a request across three lanes — Users, MLflow, Developer — in seven steps: (1) Ask — a user asks the Airbnb assistant. (2) Trace — the app logs a trace to its experiment. (3) Rate — the user picks Yes or No, plus a comment. (4) Assess — user_feedback is saved on the trace. (5) Curate — the developer's search_traces() finds the No answers for the evaluation dataset. (6) Fix — change the agent and re-run evaluate(). (7) Promote — register a new version and move the @champion alias; the app serves the new champion. This cycle — real user feedback becoming the next evaluation dataset, becoming the next deployed version — is the whole point of Modules 1-2's champion-alias architecture, now shown closing the loop it was always built for.

D2. 搭建反馈循环。课程自己的这张泳道图，把一次请求的流转，分到用户、MLflow、开发者三条泳道里，走完七步：（1）问——用户向 Airbnb assistant 提问。（2）追踪——app 把 trace 记录到它的 experiment 里。（3）评价——用户选 Yes 或 No，再加一句评论。（4）评估——user_feedback 被保存到这条 trace 上。（5）整理——开发者用 search_traces() 把那些 No 的答案找出来，放进评测数据集。（6）修复——改 agent，重跑 evaluate()。（7）晋升——注册一个新版本，把 @champion 别名移过去；app 开始服务这个新的 champion。这个循环——真实用户的反馈变成下一个评测数据集，再变成下一个部署版本——正是 Module 1、2 里一直讲的 champion 别名架构真正要达成的目的，这里第一次把这个循环完整地走通了一遍。

E Integration with Unity Catalog

E1. Governance for evaluation. Unity Catalog is the governance layer across the whole workflow: agent registration (dependencies, access controls, aliases like @champion), dataset storage (versioned, governed evaluation datasets), trace storage (SQL-queryable, shareable across teams), and lineage (from datasets to metrics to agent versions).

E1. 评测的治理层。Unity Catalog 是整个工作流的治理层：agent 注册（依赖关系、访问控制、像 @champion 这样的别名）、数据集存储（有版本管理、被治理的评测数据集）、trace 存储（可以用 SQL 查询，能跨团队共享）、血缘关系（从数据集到指标到 agent 版本，全程可追溯）。

A Model Serving vs. Databricks Apps

A1. Two deployment targets for the same registered agent. agents.deploy() (Model Serving) is a single function call: infrastructure provisioned automatically with limited control, agent code logged as an MLflow artifact, inference tables/tracing/the Review App built in. Databricks Apps (the recommended path, and what agent-airbnb-assistant actually is) is Git-based: bundles with explicit auth in databricks.yml, full control over code and server configuration, agent code running as an async FastAPI server (MLflow AgentServer, runnable locally with uv run start-app), a chat UI and an /invocations endpoint built in. Model Serving suits quick prototyping and existing deployments not yet due for migration; Apps is recommended for new production deployments needing Git-based CI/CD, local dev, and full serving-infrastructure control. Critically: both support MLflow tracing, and mlflow.genai.evaluate() works identically against either — this course's entire evaluation framework is deployment-agnostic by design.

A1.同一个注册好的 agent，有两个可以部署的目标。agents.deploy()（Model Serving）是一次函数调用：基础设施自动配置、控制权有限，agent 代码作为 MLflow artifact 记录，自带 inference table、tracing 和 Review App。Databricks Apps（推荐路径，也是 agent-airbnb-assistant 的真实身份）是基于 Git 的：用 bundle 配合 databricks.yml 里显式的鉴权，对代码和服务器配置有完全的控制权，agent 代码是以一个异步 FastAPI 服务器形式运行（MLflow AgentServer，可以用 uv run start-app 在本地跑），自带聊天界面和一个 /invocations 端点。Model Serving 适合快速原型验证、以及还没到迁移时机的已有部署；Apps 是推荐用于需要基于 Git 的 CI/CD、本地开发、以及对服务基础设施有完全控制权的新生产部署的路径。关键是：两者都支持 MLflow tracing，mlflow.genai.evaluate() 在两者上的表现完全一致——这门课整套评测框架，从设计上就是跟部署方式无关的。

B Migrating from Model Serving to Databricks Apps

B1. Four migration steps: download the agent's MLflow artifacts; restructure class methods into decorated functions; configure the app in databricks.yml; deploy with databricks bundle deploy. What changes: agent code moves from a class-based ResponsesAgent with predict()/predict_stream() to module-level @invoke()/@stream() decorated functions; configuration moves from an MLmodel file plus model config YAML to databricks.yml resource declarations; execution shifts from synchronous to async (async def recommended); the deploy command changes from agents.deploy() to databricks bundle deploy. What stays the same, and this is the part worth remembering: core agent logic (tools, LLM calls, prompts), MLflow tracing and evaluation integration, Unity Catalog tool registration, and the request/response payload format. The migration is a packaging and execution-model change, not a rewrite of what the agent actually does or how it's evaluated.

B1.迁移分四步：下载 agent 的 MLflow artifact；把基于类的方法重构成装饰器函数；在 databricks.yml 里配置这个 app；用 databricks bundle deploy 部署。会变的东西：agent 代码从一个基于类的 ResponsesAgent（带 predict()/predict_stream()）变成模块级别的 @invoke()/@stream() 装饰函数；配置从一个 MLmodel 文件加模型配置 YAML，变成 databricks.yml 里的资源声明；执行方式从同步变成异步（推荐用 async def）；部署命令从 agents.deploy() 变成 databricks bundle deploy。不会变的东西，这才是值得记住的部分：核心 agent 逻辑（工具、LLM 调用、prompt）、MLflow tracing 和评测的集成方式、Unity Catalog 工具注册、请求/响应的数据格式。这次迁移改变的是打包方式和执行模型，不是 agent 实际做什么、或者怎么被评测这件事本身。

C1. Three approaches, no-code to code-first. C1. 三种方式，从无代码到代码优先。Knowledge Assistant（遗留方案）：自带 AI Search 索引，自己选切分策略，最多挂 10 种数据源——对检索流程有完全的控制权，但是一条遗留路径。Genie Agent（托管，推荐的声明式方案）：声明 agent 该处理什么数据或文档——表用于结构化查询，UC volume 用于文档搜索——平台负责处理工具编排和查询生成。Custom Agent（代码优先）：用 OpenAI Agents SDK、LangGraph，或任何 Python 框架，自己写 agent 逻辑、工具和编排，然后部署成 Databricks App——这整门课里的 airbnb agent 走的正是这条路。

Adoption Plan The Lego-Brick Model — Step-by-Step Adoption for FM Insight

A The Brick Catalog — What Snaps Onto What

A1. The one brick everything else needs. MLflow Tracing (autolog, or manual @mlflow.trace) is the foundation plate. Nothing else in Folder 3 — no judge, no evaluation run, no feedback assessment, no monitoring — works without it, because every one of them reads or writes a trace. The good news: tracing alone is a complete, valuable, shippable brick on its own. Turning it on gives FM Insight visibility into what an agent actually did — inputs, outputs, tool calls, latency, token counts — with zero judges, zero datasets, zero evaluation code. That's worth doing in week one for its own sake.

A1. 所有其他积木都离不开的那一块。MLflow Tracing（自动打点，或者手动用 @mlflow.trace）是地基板。Folder 3 里其他任何东西——判官、评测跑批、反馈评估、生产监控——都离不开它，因为它们每一个都要读或写 trace。好消息是：tracing 本身就是一块完整、有独立价值、可以单独上线的积木。单独打开它，FM Insight 就能看到一个 agent 到底做了什么——输入、输出、工具调用、延迟、token 数量——完全不需要判官、数据集、或者评测代码。光是这一点，第一周就值得单独做。

A2. Bricks that snap directly onto tracing — no dataset required. Three scorer types plug straight into a live trace, one trace at a time, with no evaluation harness needed: Guideline judges (plain-language rules, zero code — the cheapest brick in the whole set), Built-in judges (Correctness, Safety, RelevanceToQuery, the Retrieval* family — pre-built, just point them at a trace), and Developer feedback (a human annotating a trace directly in the MLflow UI with an Expectation or a Feedback assessment — no judge at all, just a reviewer's own eyes). Any one of these three can be adopted alone, in any order, the moment tracing exists.

A2. 直接咬合到 tracing 上的积木——不需要数据集。有三种判官类型可以直接插在一条活的 trace 上，一条一条来，完全不需要评测框架：Guideline 判官（纯自然语言规则，零代码——整套积木里最便宜的一块）、内置判官（Correctness、Safety、RelevanceToQuery，还有 Retrieval* 这一族——预先搭好的，直接指向一条 trace 就能用）、开发者反馈（一个人直接在 MLflow 界面里给 trace 加一个 Expectation 或 Feedback 评估——根本不需要判官，就是审核者自己的眼睛）。这三块里的任何一块，只要有了 tracing，就可以单独采用，顺序随意。

A3. Bricks that need a scorer plus something to run it against. The Custom judge brick (make_judge() or @scorer) snaps onto the same connection point as A2's judges, but is itself a prerequisite for domain checks nothing pre-built covers — a USSGL posting-correctness check, an audit-citation-completeness check. The Offline evaluation harness (a curated dataset plus mlflow.genai.evaluate()) is the next layer up: it needs tracing and at least one scorer type (built-in, guideline, or custom — any one works), but it adds the part none of A2's bricks have alone: a repeatable, gate-the-release run across many rows at once. The champion/challenger UC alias pattern sits on top of the harness: it needs an agent already registered in Unity Catalog, and it's the mechanism that turns "this run passed" into "this version is now live."

A3. 需要一个判官、再加点东西让它跑起来的积木。自定义判官这块积木（make_judge() 或 @scorer）跟 A2 里的判官咬合在同一个连接点上，但它本身是做那些没有现成判官能覆盖的业务检查的前提——比如 USSGL 过账正确性检查、审计引用完整性检查。离线评测框架（一个整理好的数据集，加上 mlflow.genai.evaluate()）是再往上一层：它需要 tracing，还需要至少一种判官（内置、guideline、自定义，任选一种都行），但它加上了 A2 那些积木单独都没有的东西：一次能跑很多行、可重复、可以用来卡发布关口的评测。champion/challenger UC 别名这个模式搭在评测框架上面：它需要一个已经在 Unity Catalog 里注册好的 agent，它的作用是把"这次跑通过了"变成"这个版本现在正式上线了"。

A4. Bricks that need a deployed agent, not just a notebook. SME feedback via a deployed app needs the agent running somewhere with a chat UI — Model Serving or Databricks Apps, either works — and needs tracing underneath it, but needs nothing from A3's judges or harness at all; an SME can rate answers Yes/No long before any automated judge exists. Production monitoring (.register()/.start()) needs tracing plus at least one scorer that supports it (built-in, make_judge(), Guidelines, or @scorer — not a direct Scorer subclass), but doesn't need the offline harness to have ever run, though it's far more useful paired with one. UC trace storage (the four-tables-plus-two-views pattern) is a pure storage-backend swap: it needs only tracing, and nothing else in the stack cares whether traces live in the default MLflow store or in Unity Catalog tables underneath them.

A4. 需要一个真正部署出去的 agent、不只是一个 notebook 的积木。通过部署的 app 收集 SME 反馈需要 agent 真的跑在某个带聊天界面的地方——Model Serving 或 Databricks Apps 都行——下面需要有 tracing，但完全不需要 A3 里的判官或评测框架；一个 SME 可以在任何自动判官存在之前，就先用 Yes/No 给答案打分。生产监控（.register()/.start()）需要 tracing，再加上至少一种支持它的判官（内置、make_judge()、Guidelines，或 @scorer——不能是直接继承 Scorer 的子类），但不需要离线评测框架曾经跑过，不过跟它搭配起来用会更有价值。UC trace 存储（四张表加两个视图那套模式）是一次纯粹的存储后端替换：它只需要 tracing，整套体系里其他任何部分都不关心 trace 到底存在默认的 MLflow 存储里，还是存在底下的 Unity Catalog 表里。

A5. The one brick that's off to the side entirely. The deployment pattern choice (Genie Agent vs. Custom Agent, Model Serving vs. Databricks Apps) is orthogonal to the entire stack above. It can be decided at any point, independently, and changing it later doesn't require re-adopting anything else — the Appendix's own point, "evaluation techniques apply regardless of deployment method," is exactly this decoupling.

A5. 完全独立于整套体系之外的那一块。部署方式的选择（Genie Agent vs. Custom Agent，Model Serving vs. Databricks Apps）跟上面整套体系是正交的。可以在任何时候单独做这个决定，以后改变它也不需要重新采用其他任何东西——附录自己说的那句话，"评测技术跟部署方式无关"，说的正是这种解耦关系。

B A Phased Rollout for FM Insight

B1. A suggested order that follows the dependency stack in A, sized to fit alongside DoW audit-remediation work rather than as a separate platform project: Phase 0 (weeks 1-2, one brick): turn on tracing for one FM Insight agent end to end — a GFEBS or Navy ERP query agent is a reasonable first target. No judges, no dataset, no gate. The deliverable is visibility: can the platform team actually see what the agent did on every call. Phase 1 (weeks 3-4, cheapest snap-ons): add Guideline judges (plain-language rules — no code) and Developer feedback (platform team annotating traces directly in the MLflow UI). Both plug straight into Phase 0's tracing with zero new infrastructure.

B1.一个大致按 A 节的依赖关系排列的建议顺序，节奏要能跟上 DoW 审计整改本身的工作，而不是另起一个独立的平台项目：第 0 阶段（第 1-2 周，一块积木）：给某一个 FM Insight 的 agent 全程打开 tracing——一个查询 GFEBS 或 Navy ERP 的 agent，是个合理的第一个目标。不需要判官、不需要数据集、不设任何关口。这一阶段要交付的东西是"可见性"：平台团队能不能真的看到这个 agent 每一次调用都做了什么。第 1 阶段（第 3-4 周，最便宜的几块积木）：加上 Guideline 判官（纯自然语言规则，不用写代码）和开发者反馈（平台团队直接在 MLflow 界面里给 trace 打标注）。这两块都能直接插在第 0 阶段的 tracing 上，不需要任何新的基础设施。

B2. Phase 2 (weeks 5-8, the first real gate): curate a first FM-specific evaluation dataset — real GFEBS/Navy ERP query-response pairs with known-correct answers and known edge cases — wire up the built-in judges (Correctness, Safety, RelevanceToQuery), and run the offline evaluation harness. This is the first point where "did this agent pass or fail" becomes a reproducible, documented answer rather than a spot check. Phase 3 (weeks 9-12, domain-specific judges plus promotion): write custom judges for checks nothing pre-built covers — a USSGL posting-correctness judge, an audit-citation-completeness judge — and formalize the champion/challenger UC alias so a new version only goes live after it passes the Phase 2 harness.

B2.第 2 阶段（第 5-8 周，第一个真正的关口）：整理第一份专门针对 FM 的评测数据集——真实的 GFEBS/Navy ERP 查询-回答对，带有已知正确答案和已知边界情况——接上内置判官（Correctness、Safety、RelevanceToQuery），跑离线评测框架。这是"这个 agent 到底过没过关"第一次变成一个可复现、有文档记录的答案，而不是随手抽查。第 3 阶段（第 9-12 周，业务专属判官加晋升机制）：为那些没有现成判官能覆盖的检查写自定义判官——比如一个 USSGL 过账正确性判官、一个审计引用完整性判官——并且把 champion/challenger UC 别名机制正式确立下来，让一个新版本只有在通过第 2 阶段的评测框架之后才能上线。

B3. Phase 4 (quarter 2, open the feedback loop to real users): deploy as a Databricks App (decide the deployment pattern here, per A5 — independently of everything above it) and open SME feedback to the preparers, reviewers, and certifying officials who would actually use the agent, closing File 27's full Ask-Trace-Rate-Assess-Curate-Fix-Promote loop for the first time. Phase 5 (quarter 2-3, the audit-evidence layer): turn on production monitoring (.register()/.start()) and migrate trace storage into Unity Catalog tables — the piece that makes every agent decision SQL-queryable, governed, and retained long enough to matter when an auditor eventually asks for it. Each phase is independently useful and independently defensible on its own if the timeline slips; none of it requires committing to the full stack up front.

B3.第 4 阶段（第二季度，把反馈循环向真实用户打开）：部署成一个 Databricks App（在这里按 A5 的说法决定部署方式——跟上面所有阶段都无关，可以独立决定），把 SME 反馈向真正会用到这个 agent 的编制人员、复核人员、认证官员打开，第一次把 File 27 讲的那套完整的"问-追踪-评价-评估-整理-修复-晋升"循环真正闭合起来。第 5 阶段（第二到第三季度，审计证据层）：打开生产监控（.register()/.start()），把 trace 存储迁移到 Unity Catalog 的表里——这一块，让每一个 agent 的决策都变成可以用 SQL 查询、受治理、保留时间足够长的记录，等审计人员真的来问的时候用得上。每一个阶段单独拿出来都有用、单独拿出来也都站得住脚，哪怕时间表往后推了也没关系；这整套东西不需要一开始就承诺全盘采用。

C Snapping a Brick Off Again

C1. The same connection points that let a brick snap on let it snap off without collateral damage, because nothing downstream holds a hard reference to how an upstream piece is implemented — only to the interface it exposes (a trace; a Feedback object; a registered UC model behind an alias). Swapping Guideline judges for Custom judges, moving from Model Serving to Apps, or turning off production monitoring during a quiet period, each changes one brick without requiring any other brick in the stack to be touched. This is the practical payoff of the Lego framing: FM Insight can try a piece, decide it isn't earning its keep, and remove it, which is a much easier sell to a program office than "adopt the platform or don't."

C1.能让一块积木咬合上去的那个连接点，同样也能让它干净地拆下来，不会连带损坏别的东西，因为下游的任何东西都没有硬编码地依赖上游那一块具体是怎么实现的——只依赖它对外露出的接口（一条 trace；一个 Feedback 对象；一个挂着别名的、注册过的 UC 模型）。把 Guideline 判官换成自定义判官、从 Model Serving 换成 Apps、或者在一段平静期暂时关掉生产监控，每一次改动都只动了一块积木，不需要碰整套体系里的任何其他部分。这正是乐高比喻在实际中的好处：FM Insight 可以先试一块，发现它不值得留着，然后拆掉它——这比"要么整套采用，要么一点都不采用"，对一个项目办公室来说要容易接受得多。
